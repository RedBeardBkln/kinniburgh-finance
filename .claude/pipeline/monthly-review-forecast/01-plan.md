# Plan: monthly-review-forecast

## Restated goal

Add forward-looking signal to the monthly household review: (1) a
per-tag projected end-of-period total next to each budgetHealth row, using
the existing `projectPeriodEndSpend()`, and (2) a retrospective "how
accurate was last month's mid-month projection" comparison, reconstructed
from stored transaction history (no new tracking table). Both must be
computed once at generation time and stored in the existing `MonthlyReview.data`
JSON blob, and must reach the review however it's produced — including the
monthly cron, not just the manual "Generate/Regenerate" button.

## Scope

**In scope:**
- New pure lib module `lib/review-forecast.ts`: period-math helpers +
  retrospective reconstruction/selection logic, unit tested.
- New shared, non-`"use server"` module `lib/monthly-review-build.ts` that
  owns the `ReviewData` type and the actual DB-driven review-building logic
  (moved out of `actions/monthly-review.ts`, see "Discovered issue" below).
- `actions/monthly-review.ts`: slimmed down to `requireAuth()` + period
  validation + delegate to `buildMonthlyReviewData()` + upsert + revalidate.
- `app/api/cron/monthly-review/route.ts`: delegate to the same
  `buildMonthlyReviewData()` instead of its own separately-maintained inline
  computation (see "Discovered issue").
- `app/review/[year]/[month]/page.tsx`: render the two new pieces of
  information; import the shared `ReviewData` type instead of its own local
  duplicate; defensively handle old stored review rows that predate these
  fields.
- New test file `lib/__tests__/review-forecast.test.ts`.

**Out of scope / explicitly NOT changing:**
- `lib/spend-forecast.ts` and `lib/budget-pace.ts` — no signature or
  behavior changes, imported as-is.
- No new Prisma model/migration (see Risks/unknowns #1 for reasoning).
- No backfill of previously-generated `MonthlyReview` rows — old stored JSON
  simply won't have the new fields until a period is regenerated.
- No change to the cron route's notification body copy (still based on
  over-budget/behind-accrual counts) — not asked for, and adding forecast
  language there would expand scope beyond the review itself.
- No change to `checkBudgetPace`/`lib/notifications.ts` — that's a separate,
  already-shipped feature (early alerting); this task is the deliberate,
  read-when-you-choose review surface, which is intentionally allowed to be
  more verbose/complete than the notification path.
- No changes to `accountSnapshot`, `upcomingBills`, or `accrualStatus`
  sections beyond incidental ones caused by delegating cron to the shared
  builder (see Risks/unknowns #3 for the specific behavioral deltas that
  fixes bundles in).

## Discovered issue that shapes this plan

`app/api/cron/monthly-review/route.ts` does **not** call
`generateMonthlyReview()`. It has its own fully separate, hand-duplicated
inline implementation of the same budgetHealth/accountSnapshot/upcomingBills/
accrualStatus computation, writing to the same `MonthlyReview.data` JSON
column. The two implementations have already drifted (see Risks/unknowns #3).
If this task only enriches `actions/monthly-review.ts`, the monthly cron —
the task's own stated "generated by" path, and the only fully-automated
path — would keep producing reviews with **no** forecast information,
defeating the point of the task.

Simply making the cron route call `generateMonthlyReview(period)` directly
is not viable either: `generateMonthlyReview`'s first line is
`await requireAuth()`, which calls NextAuth's `auth()` and throws if there is
no session. The cron route authenticates via a `Bearer ${CRON_SECRET}`
header, not a user session — there is no session cookie on that request, so
`requireAuth()` would throw "Unauthorized" on every cron run.

**Resolution:** extract the actual DB-querying/computation logic (all four
existing sections plus the two new ones) into a new, non-`"use server"`
module, `lib/monthly-review-build.ts`, exporting an async
`buildMonthlyReviewData(period)` function and the `ReviewData` type. This
function is not a server action — it's an ordinary async function, safe to
import from both `actions/monthly-review.ts` (which does its own
`requireAuth()` first, then calls it, then upserts) and
`app/api/cron/monthly-review/route.ts` (which keeps its own bearer-secret
check, then calls it, then upserts and fires the notification exactly as it
does today). This gives one source of truth for how a review is computed,
matching the "pure function / thin DB call site" pattern this repo already
uses elsewhere, and it's the only way to guarantee the new forecast fields
actually reach the automated monthly review. This is flagged explicitly as a
scope decision, not sprung silently — see Risks/unknowns #3 for the specific
pre-existing divergences this consolidation will also incidentally fix.

## Approach

### Step 1 — `lib/review-forecast.ts` (pure, new file)

No DB imports, no `"use server"`. Imports `projectPeriodEndSpend`,
`MonthlySpendPoint`, `SpendForecast`, `ForecastConfidence` from
`./spend-forecast`. Money in Decimal (dollars, matching `Transaction.amount`'s
actual unit — `Decimal(14,2)` dollars, not cents; only the JSON-stored
`ReviewData` shape uses cents, at the boundary in `lib/monthly-review-build.ts`).

```ts
export const REVIEW_FORECAST_TRAILING_MONTHS = 3; // shared window for both
  // the forward budgetHealth projection and the retrospective reconstruction,
  // so query windows and projectPeriodEndSpend's own default never drift
  // apart via two different magic numbers.
export const MAX_ACCURACY_ROWS = 5;
export const MIN_NOTABLE_MISS_AMOUNT = new Decimal(10); // $10 dollars — a
  // miss below this is rounding noise, not a signal worth a household's
  // attention in a monthly review.

/** "YYYY-MM" immediately before `period`, handling year rollover
 *  ("2026-01" -> "2025-12"). Throws on malformed input. */
export function previousPeriod(period: string): string

/** Deterministic "representative point" used to reconstruct what a forecast
 *  would have said partway through `period`: the period's calendar
 *  midpoint day (ceil(daysInPeriod / 2)), at UTC midnight. Depends only on
 *  the period string (no "now"), so regenerating a review for the same
 *  period always reconstructs the same historical projection. Throws on
 *  malformed input. */
export function periodMidpointDate(period: string): Date

export interface ForecastAccuracyResult {
  projected: Decimal;      // absolute magnitude — reconstructed midpoint projection
  actual: Decimal;         // absolute magnitude — the now-known final total
  missAbs: Decimal;        // |actual - projected|, absolute magnitude
  percentOff: number | null; // round(missAbs / actual * 100); null when actual is 0 (div-by-zero guard)
  direction: "over" | "under" | "exact"; // projected > actual => "over"; projected < actual => "under"; missAbs===0 => "exact"
  confidence: ForecastConfidence; // straight passthrough from the reconstructed SpendForecast — never hidden
  reconstructedForecast: SpendForecast; // full underlying forecast (method, trailingMonthsUsed, etc.) for callers/UI that want more detail
}

/**
 * Reconstructs what projectPeriodEndSpend() would have projected partway
 * (periodMidpointDate(period)) through a now-complete `period`, using only
 * the transaction activity that existed by that point plus trailing history
 * strictly before `period` — then compares it to the period's real final
 * total. All DB aggregation is the caller's job (matching lib/budget-pace.ts's
 * pure/DB split); this function does only the Decimal math.
 */
export function reconstructForecastAccuracy(opts: {
  period: string;              // the now-complete period being retrospectively evaluated
  spendAtMidpoint: Decimal;    // signed sum of period's transactions with postedAt through periodMidpointDate(period) inclusive
  actualFinal: Decimal;        // signed full-period actual total
  history: MonthlySpendPoint[]; // periods strictly before `period` — full, complete totals
  trailingMonths?: number;     // default REVIEW_FORECAST_TRAILING_MONTHS
}): ForecastAccuracyResult

export interface TaggedForecastAccuracy {
  tagName: string;
  entityName: string;
  result: ForecastAccuracyResult;
}

/**
 * Narrows a full set of per-tag reconstructions down to the "notable
 * misses" worth printing in a review: drops low-confidence reconstructions
 * (too little trailing history to mean anything — same signal
 * projectPeriodEndSpend already exposes, not new logic) and misses at or
 * below minMissAmount, sorts the remainder by absolute dollar miss
 * (largest first — dollar magnitude is what a household actually cares
 * about, not percent-off on a trivially small budget line), and caps to
 * maxRows. Returns [] when nothing qualifies — never throws.
 */
export function selectNotableAccuracyRows(
  rows: TaggedForecastAccuracy[],
  opts?: { maxRows?: number; minMissAmount?: Decimal }
): TaggedForecastAccuracy[]
```

### Step 2 — `lib/__tests__/review-forecast.test.ts`

Follow the existing test-file conventions (`D = (s) => new Decimal(s)`,
`d = (iso) => new Date(iso + "T00:00:00Z")`, `describe`/`it`/`expect`).

**`previousPeriod`:**
1. `"2026-09"` → `"2026-08"`.
2. `"2026-01"` → `"2025-12"` (year rollover).
3. `"2026-12"` → `"2026-11"`.
4. Invalid formats (`"26-09"`, `"2026-9"`, `""`) throw.

**`periodMidpointDate`:**
1. `"2026-09"` (30-day month) → `2026-09-15T00:00:00Z`.
2. `"2026-08"` (31-day month) → `2026-08-16T00:00:00Z`.
3. `"2026-02"` (28-day, non-leap) → `2026-02-14T00:00:00Z`.
4. `"2028-02"` (29-day leap year — 2028 is divisible by 4, not a century
   year) → `2028-02-15T00:00:00Z` (ceil(29/2) = 15).
5. Invalid format throws.

**`reconstructForecastAccuracy`** — all worked with exact Decimal values
(period `"2026-09"`, 30 days, midpoint day 15 ⇒ `daysElapsed = daysRemaining = 15`,
so blended = `(pace + trailingAverage) / 2`):

1. **Exact match, high confidence** — `spendAtMidpoint = D("-300")`,
   `history = [-600, -580, -620]` (avg `-600`, matches spend-forecast's own
   test 1 numbers). `pace = -300*30/15 = -600`. `blended = (-600 + -600)/2 = -600`.
   `actualFinal = D("-600")`. Expect: `projected.toString() === "600"`,
   `actual.toString() === "600"`, `missAbs.toString() === "0"`,
   `percentOff === 0`, `direction === "exact"`, `confidence === "high"`.

2. **Under-projection** (household ended up spending *more* than the
   midpoint projection said) — `spendAtMidpoint = D("-500")`,
   `history = [-300, -280, -320]` (avg `-300`). `pace = -500*30/15 = -1000`.
   `blended = (-1000 + -300)/2 = -650`. `actualFinal = D("-800")`. Expect:
   `projected.toString() === "650"`, `actual.toString() === "800"`,
   `missAbs.toString() === "150"`, `percentOff === 19` (150/800 = 18.75% →
   rounds to 19), `direction === "under"`, `confidence === "high"`.

3. **Over-projection** — `spendAtMidpoint = D("-1000")`, same history
   (avg `-300`). `pace = -1000*30/15 = -2000`. `blended = (-2000 + -300)/2 = -1150`.
   `actualFinal = D("-700")`. Expect: `projected.toString() === "1150"`,
   `actual.toString() === "700"`, `missAbs.toString() === "450"`,
   `percentOff === 64` (450/700 = 64.28…% → 64), `direction === "over"`,
   `confidence === "high"`.

4. **Low confidence (no trailing history)** — `spendAtMidpoint = D("-200")`,
   `history = []`. `pace = -200*30/15 = -400` (pace_only). `actualFinal = D("-380")`.
   Expect: `projected.toString() === "400"`, `missAbs.toString() === "20"`,
   `percentOff === 5`, `direction === "over"`, `confidence === "low"`,
   `reconstructedForecast.method === "pace_only"`. (missAbs of $20 is above
   the $10 floor, so this case exists specifically to prove
   `selectNotableAccuracyRows` excludes it for *confidence*, not magnitude —
   see selection tests.)

5. **`actualFinal` is zero — `percentOff` div-by-zero guard** —
   `spendAtMidpoint = D("-100")`, `history = []`. `pace = -200`.
   `actualFinal = D("0")`. Expect: `projected.toString() === "200"`,
   `actual.toString() === "0"`, `missAbs.toString() === "200"`,
   `percentOff === null`, `direction === "over"`.

**`selectNotableAccuracyRows`:**
1. Drops a row with `confidence === "low"` even though its `missAbs` clears
   `MIN_NOTABLE_MISS_AMOUNT` (use case 4's result above, wrapped).
2. Drops a row with `missAbs` at/below `MIN_NOTABLE_MISS_AMOUNT` (e.g. `D("5")`)
   even at high confidence.
3. Caps to `MAX_ACCURACY_ROWS` (5) when more than 5 qualifying rows are
   passed, keeping the 5 with the largest `missAbs`, sorted descending.
4. Returns `[]` for `[]` input and for input where nothing clears the
   filters.
5. Custom `opts.maxRows`/`opts.minMissAmount` override the defaults.

### Step 3 — `lib/monthly-review-build.ts` (new, DB-touching, not `"use server"`)

Move the `ReviewData` interface here (single source of truth — both
`actions/monthly-review.ts` and `app/review/[year]/[month]/page.tsx`
currently declare their own copies; both should import this one instead).
Extend it additively:

```ts
interface ReviewData {
  period: string;
  generatedAt: string;
  budgetHealth: Array<{
    tagName: string;
    entityName: string;
    budgetedCents: number;
    actualCents: number;
    percentUsed: number;
    status: "ok" | "warning" | "over";
    // NEW — forward projection for this period:
    projectedCents: number;        // abs(forecast.projectedTotal) in cents
    projectedPercentUsed: number;  // round(projectedCents / budgetedCents * 100); 0 when budgetedCents is 0
    forecastConfidence: "low" | "medium" | "high";
    forecastMethod: "blended" | "pace_only";
  }>;
  accountSnapshot: [...unchanged...];
  upcomingBills: [...unchanged...];
  accrualStatus: [...unchanged...];
  // NEW — retrospective accuracy for the prior period:
  forecastAccuracyPeriod: string | null; // the prior "YYYY-MM" this section evaluates; null when there were no budgeted tags for that period to evaluate (e.g. first review ever generated)
  forecastAccuracy: Array<{
    tagName: string;
    entityName: string;
    projectedCents: number; // abs, reconstructed at that period's midpoint
    actualCents: number;    // abs, actual final total
    missCents: number;      // abs(actual - projected)
    percentOff: number | null;
    direction: "over" | "under" | "exact";
    confidence: "low" | "medium" | "high";
  }>;
}

export async function buildMonthlyReviewData(period: string): Promise<ReviewData>
```

`buildMonthlyReviewData` body, in order:

1. Validate `period` matches `/^\d{4}-\d{2}$/` (throw if not — this function
   is only ever called with a value the caller has already validated or
   programmatically constructed, so a thrown error, not a soft `{error}`
   return, is appropriate here).
2. **Budget health + forward projection** (extends the existing block):
   - Existing: `db.budget.findMany({ where: { period }, include: { tag, entity } })`
     and the existing `tagSpendRows` query (`SUM(t.amount)`, grouped by
     `entityId, tagId`, filtered `archivedAt IS NULL AND transferPairId IS NULL`
     and date-bounded to the period) — keep as-is.
   - Change: alongside the existing `spendMap` (abs cents), also build a
     `spendDecimalMap: Map<string, Decimal>` (signed, dollars) from the same
     `tagSpendRows` rows — no extra query needed.
   - New query: trailing-months history, entity+tag scoped, same shape as
     `checkBudgetPace`'s `historyRows` in `lib/notifications.ts` but grouped
     by `entityId` too (this file already keys by `${entityId}:${tagId}`,
     unlike budget-pace which is tag-only):
     ```sql
     SELECT t."entityId", tt."tagId", to_char(t."postedAt",'YYYY-MM') AS period,
            SUM(t.amount)::text AS total
     FROM "Transaction" t
     JOIN "TransactionTag" tt ON tt."transactionId" = t.id
     WHERE t."archivedAt" IS NULL AND t."transferPairId" IS NULL
       AND t."postedAt" >= ${historyStart} AND t."postedAt" < ${monthStart}
     GROUP BY t."entityId", tt."tagId", period
     ```
     where `historyStart = new Date(Date.UTC(year, month - 1 - REVIEW_FORECAST_TRAILING_MONTHS, 1))`.
     Build `historyMap: Map<string, MonthlySpendPoint[]>` keyed
     `${entityId}:${tagId}`.
   - For each budget row, call
     `projectPeriodEndSpend({ period, spendToDate: spendDecimalMap.get(key) ?? new Decimal(0), asOfDate: new Date(), history: historyMap.get(key) ?? [], trailingMonths: REVIEW_FORECAST_TRAILING_MONTHS })`
     directly (no wrapper needed — this is pure data marshaling around an
     already-tested pure function, matching the precedent of
     `checkBudgetPace` calling `evaluateBudgetPace`/`projectPeriodEndSpend`
     inline without its own dedicated unit tests). Derive
     `projectedCents = Math.round(forecast.projectedTotal.abs().toNumber() * 100)`,
     `projectedPercentUsed = budgetedCents > 0 ? Math.round(projectedCents / budgetedCents * 100) : 0`,
     `forecastConfidence = forecast.confidence`, `forecastMethod = forecast.method`.
3. Account snapshot / upcoming bills / accrual status: move unchanged from
   `actions/monthly-review.ts`'s current logic (this is the version to keep
   — it already has the `archivedAt`/`transferPairId`/entity-scoping
   correctness the cron route's duplicate lacks; see Risks/unknowns #3).
4. **Retrospective forecast accuracy** (new block):
   - `const priorPeriod = previousPeriod(period);`
   - `const priorBudgets = await db.budget.findMany({ where: { period: priorPeriod }, include: { tag: true, entity: true } });`
   - If `priorBudgets.length === 0`: set `forecastAccuracyPeriod = null`,
     `forecastAccuracy = []`, skip the rest of this block entirely (no
     prior-period budget lines exist to evaluate — e.g. the very first
     review ever generated).
   - Otherwise: compute `priorStart`/`priorEnd` (month bounds of
     `priorPeriod`), `midpointDate = periodMidpointDate(priorPeriod)`,
     `midpointExclusive = new Date(midpointDate.getTime() + 24*60*60*1000)`
     (transactions posted through and including the midpoint day).
   - Query full-period actuals for `priorPeriod` (same shape as the main
     `tagSpendRows` query, date-bounded `priorStart..priorEnd`).
   - Query midpoint-partial totals for `priorPeriod` (same shape,
     date-bounded `priorStart..midpointExclusive`).
   - Query trailing history strictly before `priorPeriod`
     (`historyStart = Date.UTC(priorYear, priorMonth - 1 - REVIEW_FORECAST_TRAILING_MONTHS, 1)`
     through `priorStart`), same shape as the forward-projection history
     query.
   - Build three `Map<string, ...>` keyed `${entityId}:${tagId}` (actual
     Decimal, midpoint-partial Decimal, `MonthlySpendPoint[]`).
   - For each `priorBudgets` row, call `reconstructForecastAccuracy({ period: priorPeriod, spendAtMidpoint: midpointMap.get(key) ?? new Decimal(0), actualFinal: actualMap.get(key) ?? new Decimal(0), history: historyMap.get(key) ?? [] })`,
     collect as `TaggedForecastAccuracy[]` (`tagName: b.tag.shortName`,
     `entityName: b.entity.name`).
   - `const notable = selectNotableAccuracyRows(candidates);`
   - Map `notable` to the stored cents shape (`Math.round(x.toNumber() * 100)`
     for `projected`/`actual`/`missAbs`, passthrough `percentOff`/`direction`/`confidence`).
   - `forecastAccuracyPeriod = priorPeriod`.
5. Assemble and `return` the `ReviewData` object (do **not** upsert here —
   upserting stays the caller's job, matching each caller's own
   auth/side-effect needs).

  muted note instead of the card (mirrors the page's existing "No review has

  per ground rule 8), plus the same confidence label convention as above.
  Frame the section's intro copy carefully: since no projection was actually
  shown to the household last month (no snapshot mechanism existed before
  this task), phrase as "what the current projection model would have
  estimated at that point" rather than implying this is literally what was
  displayed at the time — stay factual per ground rule 8.
- Both new sections are pure Server Component rendering (plain
  numbers/strings only, no new client components needed) — matches the
  RSC read-path convention already used throughout this page; no new
  `useState`/interactivity is required for this task.

## Risks/unknowns

1. **No new Prisma model — reasoning.** `Transaction.postedAt` is an
   immutable, already-dated fact (ground rule 3), so "what would the
   projection have said as of a past date" is fully reconstructable after
   the fact by re-querying with a date-bounded `WHERE postedAt < X` clause.
   No live snapshot needed to answer "what would it have said," only to
   answer "what did it actually say" — and the task explicitly says the
   latter isn't required (nothing was ever displayed before now). Concluded
   a new model is unnecessary; flagging per the requirement to state this
   explicitly either way.

2. **Cron/action duplication (see "Discovered issue" above) — consolidation
   is a necessary, not optional, part of this task**, not scope creep: the
   feature's own stated delivery path (monthly cron) would otherwise never
   receive the new fields. Flagged prominently so the user can veto/redirect
   before the Coder builds it — this is the single largest structural change
   in this plan.

3. **Consolidation bundles in incidental fixes** to the cron route's
   pre-existing divergence from `actions/monthly-review.ts`'s logic (all
   discovered while reading both files in full):
   - Cron's `tagSpendRows`/accrual queries did **not** filter
     `transferPairId IS NULL` the way `actions/monthly-review.ts`'s do —
     internal transfers were being counted as spend in cron-generated
     reviews. Consolidating onto `buildMonthlyReviewData` fixes this.
   - Cron's accrual pro-rata used the *current calendar month*
     (`now.getUTCMonth()+1`) rather than the *target period's* month — since
     cron always targets the previous month, this was silently off by one
     month's worth of pro-rata target every time. Consolidating fixes this
     too (the kept `actions/monthly-review.ts` logic uses the target
     period's month correctly).
   - Cron's `entityName` used `b.entity.name.split(",")[0]`;
     `actions/monthly-review.ts` uses the full `entity.name`. Consolidating
     changes cron-generated reviews to show full entity names, matching
     manually-generated ones (currently the two paths render this
     differently depending on which one produced a given period's review).
   These are disclosed here as an explicit, deliberate side effect of
   fixing the duplication, not a silent behavior change — worth a callout
   in the PR/review description so the user isn't surprised by an unrelated
   diff inside the cron route.

4. **Old stored `MonthlyReview` rows have no backfill.** Every period
   generated before this ships will render without the two new sections
   (guarded to render gracefully, not crash) until someone clicks
   "Regenerate" for that period, or the next cron cycle runs. No backfill
   script is included — not asked for, and ground rule 7 doesn't require
   retroactively regenerating archived-but-not-deleted review snapshots.

5. **Judgment calls needing sign-off, all easily tunable (exported
   constants) if the user disagrees:**
   - Midpoint (`ceil(daysInPeriod / 2)`) as the reconstruction's
     representative point — the task's own example.
   - `$10` floor / top-5 cap / confidence-low exclusion for which tags
     surface in "Forecast accuracy" — chosen to keep the section from
     ballooning into a wall of numbers every month, prioritizing dollar
     magnitude over percent-off so a tiny budget's large percentage swing
     doesn't crowd out a materially larger miss elsewhere.
   - Forward-projection `asOfDate` is generation time (`new Date()`), so a
     review generated for an already-complete past period will show
     `projectedCents === actualCents` (the projection collapses to the
     known actual — `projectPeriodEndSpend` already handles this
     correctly, see its own test 6) rather than anything forward-looking;
     the forward-looking value is realized specifically when a review is
     generated/regenerated for the *current*, still-in-progress period.
     This is expected behavior given how `projectPeriodEndSpend` is
     designed, not a bug, but worth the user's awareness since it means the
     "Projected" column is only interesting information some of the time.

6. **Notification body in the cron route is intentionally left unchanged**
   (still summarizes over-budget/behind-accrual counts only) — extending it
   to mention forecast highlights would be a reasonable follow-up but isn't
   asked for here and would expand this task's diff further into
   `lib/notifications.ts`/notification-copy territory.

7. **UI verification.** This task touches a rendered page
   (`app/review/[year]/[month]/page.tsx`). No pipeline agent has browser
   access — a human must visually verify the rendered budget-health table
   (new columns, confidence badges) and the new "Forecast accuracy" card
   (populated and empty states) before this is considered done, consistent
   with every prior UI-touching task in this repo.

  `buildMonthlyReviewData`, `generateMonthlyReview`, and the cron route's
  `GET` handler. The forward-projection wiring inside
  `buildMonthlyReviewData` calls `projectPeriodEndSpend` directly with no

  `lib/__tests__/spend-forecast.test.ts` already covers.

  (confirmed convention — mocked at the function boundary), so there's no
  integration-test layer to add here; the acceptance-criteria item above
  asking the Tester to generate a period via both the button and (a
  simulated/manual) cron-shaped call and diff the stored JSON is the closest
  available check that the two paths stay in sync, and should be done as a
  manual/scripted spot-check rather than a new automated test file, matching
  how this repo already treats DB-touching code.

  spend at retrospective comparison time (div-by-zero guard), zero trailing
  history (low confidence, pace_only), a tag budgeted in the prior period

  DB queries are on different `period` values with independent budget
  lookups), first-ever review generation (`forecastAccuracyPeriod: null`),
