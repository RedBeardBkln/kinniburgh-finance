# Task request: monthly-review-forecast

Repo: D:\Repos\Personal\kinniburgh-finance

## TASK

Enrich the existing monthly household review (`actions/monthly-review.ts`'s
`generateMonthlyReview`, rendered at `app/review/[year]/[month]/page.tsx`,
generated by a monthly cron via `app/api/cron/monthly-review/route.ts`) with
forecast information, so the household gets forward-looking signal, not just
a backward-looking snapshot.

## CONTEXT

This is Tier 2, item 2 of an agreed product roadmap toward the platform's
north star: "automate as much financial work as possible" via forecast
projections that keep the household informed. Read `actions/monthly-review.ts`
IN FULL — it already computes budgetHealth (percentUsed/status per tag, but
purely a snapshot: actual-spend-so-far vs. budgeted, no forward projection),
accountSnapshot, upcomingBills, and accrualStatus, and upserts a
MonthlyReview row keyed by period. Read `app/review/[year]/[month]/page.tsx`
to see how this data is currently rendered. Also read `lib/spend-forecast.ts`
IN FULL (already built, reviewed, and merged — `projectPeriodEndSpend()`
projects a tag's likely end-of-period total from trailing-months history +
period-to-date spend, with a confidence field) and `lib/budget-pace.ts` (the
notification-facing consumer of spend-forecast, useful as a precedent for how
this codebase wires spend-forecast into other features, though note
budget-pace suppresses low-confidence/near-threshold rows — a monthly REVIEW
should behave differently, see below).

## WHAT "ENRICH WITH FORECAST ACCURACY" MEANS — resolve concretely

1. **Forward projection for the review's own period**: budgetHealth currently
   only shows spend-so-far vs. budget. Add each tag's projected end-of-period
   total via `projectPeriodEndSpend()` (reusing the already-built module, not
   reimplementing it), so the household sees not just "62% used" but "on pace
   to land at $X (Y% of budget)". This should NOT suppress low-confidence or
   near-threshold results the way `lib/budget-pace.ts` does for notifications
   — a review is a data table the household reads deliberately, not an alert
   that needs to avoid noise, so show the projection with its confidence
   level visible rather than hiding it.

2. **Retrospective "forecast accuracy"**: the roadmap language asks for "last
   month's forecast-vs-actual accuracy." There is no stored history of past
   projections to compare against (no prior snapshot mechanism exists) — so
   this must be computed RETROACTIVELY from real historical transaction data
   already in the database, not from a new tracking mechanism, unless
   genuinely necessary (state reasoning either way). Concretely: for the
   PRIOR period, reconstruct what `projectPeriodEndSpend()` would have said
   partway through that period (e.g. period midpoint, using only transaction
   data that existed as of that point) and compare it to what the tag's
   spend actually finished at. Report this as a simple accuracy signal per
   tag for tags where this comparison is meaningful (skip thin-history tags
   via the confidence field). Decide how many tags to surface this for and
   justify the choice — don't let this section balloon into an unreadable
   wall of numbers every month.

3. Decide whether this retrospective accuracy calculation happens live every
   time the review page is viewed/regenerated, or only once when the review
   is first generated for a period (follow the existing upsert-once `data`
   JSON blob pattern rather than inventing live recomputation on every page
   view, unless there's a strong reason not to).
