## Defects found (all LOW, none blocking)

1. CLAUDE.md is stale about the add action (documentation, Low). `CLAUDE.md` line ~117 still says "client sends only entity + series key ... the budget tag is linked only at 60%+ share and when no Budget, bill or recurring expense already uses it". After the tag-picker change the client also sends `tagId` (null = No tag) and an optional `name`, an explicit tag is linked without the "in use" probe, and the row's notes carry `[pattern:<key>]`. The Coder noted they did not edit CLAUDE.md in the second batch. Not covered there either: the `suppressedBy.kind "series"` rule, "a recurring expense no longer suppresses by tag alone", `lib/recurring-budget-hint*.ts`. Repro: `grep -n "client sends only entity" CLAUDE.md`. Suggested fix: update that sentence and add the marker/tag-rule/hint facts.
2. Narrow weakening of the ledger duplicate check (Low, disclosed as Deviation 1). When two records of one entity BOTH end in a parenthesis and the two differ, they are no longer treated as one obligation. Repro (also pinned in `recurring-followups-tester-diff.test.ts`): a tagged bill `Electric (Eversource)` 172 day 20 plus an untagged bill `Eversource (Heat)` 173 day 20: HEAD holds the second back, the working tree counts both (double count of ~173). Live data is unaffected (counted ledger byte-identical to HEAD for all scopes). Fix only if the owner wants the stricter rule (for example apply it only when a qualifier is a known account nickname).
3. The "Already recorded" name check ignores the owner-chosen name and is keyed to the series' default name (Low, edge case only). Repro (pinned in `recurring-followups-tester-actions.test.ts`): add the Credit Cards fee series and type the name `Maintenance Fee (Slush Funds)`; the detector still offers the Slush Funds series, but adding it (even with a different name) answers "Already recorded" and writes nothing, until that row is deleted or renamed. Needs the owner to give one series the other's qualified name on purpose.
4. Account nicknames containing parentheses (or over 60 chars) would bypass the qualifier reader (Low, latent). `trailingQualifier("Maintenance Fee (Checking (x1234))")` is null, so the account-aware rules fall back to plain word matching (both same-payee series could hide each other). Checked live: none of the 17 nicknames has parentheses or digit runs, so currently unreachable. Also note it would be an account-number-in-nickname issue anyway.

Observations (not defects, from the Coder's own open items, confirmed): when an expected date has passed unposted, the agenda block shows the next in-window date (Google One: block "next Nov 6", review list "Expected around Oct 6, not posted yet"); a nickname rename after a qualified record exists makes that record fall back to word matching; Budgets notice for a parent line that auto-sums children is described only as "no amount of its own".
