# Task Request: dashboard-accuracy-drilldown

## Owner statements (2026-10-09, verbatim)
"Review the accuracy of the widgets on the dashboard. For example, the total spent in September says $4,562.94 but this isn't correct since the mortgage payment alone is nearly that amount. Also, these widgets should be functional with drill down capabilities so you can click on them and see which data they're referencing. And the budget lines should mimic the tag format with parent categories and the child budgets underneath."

## Part A: Accuracy audit (do this first, evidence-based)
Audit EVERY widget/number on the dashboard (`app/page.tsx`, `components/dashboard/*`: summary cards "Total Budgeted / Spent This Month (or Spent in <month>) / Overspent Lines", the spending chart, the "Spending this month: top categories" cards, the budget lines table, accounts, scheduled transfers, statements and anything else rendered), for the Personal bucket and the business/all-entity buckets, for the current month and prior months (`?period=YYYY-MM`).
Known suspects visible in code (verify, do not assume):
- `totalSpend` = `db.transaction.aggregate` SUM of ALL non-archived, non-transfer-paired transactions in the month: this is a SIGNED sum including inflows (paychecks, refunds, interest) that net against spending, so it is not "total spent".
- The `transferPairId IS NULL` filter may exclude real expenses that are recorded as paired transfers (e.g. the PennyMac mortgage payment from the Mortgage & Insurance account to the loan account may be a paired transfer, so it is excluded from the total yet counted in the Mortgage tag's own line: "Mortgage $4,336 of $4,700"); also the owner's rule is that envelope transfers between own accounts are NOT spending but loan/mortgage/credit-card payments to external parties ARE expenses/liability payments: decide and document the exact definition per metric (credit card spending counted when charged vs when the card is paid: avoid double counting charge + payment).
- Per-tag spend (`TransactionTag` join) vs total: a transaction with several tags (split/multi-tag) can be counted more than once; untagged spend is not in any category card.
- Budget lines table: `app/page.tsx` ~line 116 says it does not apply the recurring-expense override that `/budgets` applies (known inconsistency); nesting uses same-account-only resolution; check parent/child double counting in totals (`getRootBudgetLineIds`).
- Period handling: UTC month boundaries vs America/New_York display for transactions posted near midnight on the 1st/last day; `?period=` selector.
- `Overspent Lines` count correctness; "Total Budgeted" vs `/budgets` page totals for the same month.
For each metric produce: the current formula, the CORRECT definition (state it plainly; ask the owner only if it is a genuine judgment call, with a recommendation), the live value shown today vs an independent recomputation straight from transactions (read-only), and the root cause of every discrepancy (e.g. reproduce September's $4,562.94 exactly and explain it line by line). Use real September 2026 and October 2026 data.

## Part B: Drill-down on every widget
Every dashboard number/card/bar/row must be clickable and show the data behind it:
- Summary cards (Total Budgeted, Spent, Overspent Lines), chart bars, category cards (an existing `category-drilldown-modal.tsx` exists: check what it does and reuse/extend), budget lines (click a line -> the transactions counted in it for that month, with the date, payee, account nickname, amount and tag; parent lines show the children and their transactions), account balances (-> that account's recent transactions), scheduled transfers, statements, the Next-30-days widget (-> the underlying items/sources).
- The drilled-down list must reconcile to the number clicked (sum of the rows equals the headline; show the sum and flag any rows excluded and why, e.g. "2 transfers between your own accounts are not counted"). Prefer deep links to existing pages with filters (e.g. `/transactions?...` if it supports tag/account/date/period filters) or an in-page drawer/modal; choose the least new code that is consistent with the app. Keyboard accessible, works on mobile width, no account numbers, preserves the active `bucket` and `period`.
- Unreconcilable or untagged remainders must be shown as their own explicit row ("Untagged", "Uncategorized"), never hidden.

## Part C: Budget lines mimic the tag hierarchy
The dashboard budget lines table must show parent categories with child budgets nested underneath, in the same hierarchy/format as the Tags page and `/budgets` (see `lib/tags.ts` path format like "Food & Drink / Groceries", `nestBudgetLines`, `lib/budget-nesting.ts`, `components/budgets/*`): parent row with its total (budgeted / spent / remaining / progress), children indented beneath it, expand/collapse if appropriate, sorted consistently with `/budgets`, parent totals = sum of children where the parent auto-sums, and no double counting in the page totals. Reuse the existing nesting helpers and presentational components from `/budgets` rather than inventing a second implementation.

## Constraints
- TypeScript strict, no `any`; Decimal money; dates UTC stored / NY displayed; `auth()` ordering unchanged; read-only queries with explicit selects; fail-soft widgets (one failing widget must not blank the dashboard); no account numbers in UI; ground rule 6 (entity separation: the "taxes"/all-entities view shows per-entity lines, never blended money where that was the existing rule); observational wording; no migration; no DB writes; no tax code; preserve LF/CRLF with binary edits.
- The dashboard already renders the Upcoming widget in a Suspense boundary: do not regress that. The branch also has an in-progress step ("carry-forward") that does not touch the dashboard: avoid its files (lib/bill-dates*, lib/budget-carry-forward*).
- Existing tests that pin dashboard behavior may need updates only where they encode wrong numbers (state why).
- Read-only live checks via a temporary repo-root script (`node_modules/.bin/tsx --env-file=.env ./_x.ts`, delete afterwards). Token-frugal.

## Deliverable
`01-plan.md`: the audit table (metric, current formula, correct definition, today's value vs recomputed value, root cause) incl. the exact explanation of $4,562.94; the fix design per metric with one shared pure helper for dashboard spend (so the dashboard, `/budgets`, monthly review and drill-down agree); the drill-down design and routes/components; the hierarchy design; file list; test list (golden numbers for Sept/Oct 2026 from live data as fixtures where safe); risks; plain-language owner questions with recommended defaults (e.g. should mortgage principal count as spending, how credit cards are counted, whether income is shown separately).
