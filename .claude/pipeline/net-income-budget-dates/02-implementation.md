## Deviations from the plan
1. A Budget row is usable only when its frequency equals the bill's (plan only excluded a lump-sum bill getting a non-lump row). Reason: the per-occurrence amount depends on the frequency, so mixing would change amounts. Effect: the Lexus-style weekly-vs-monthly mismatch keeps the bill's own schedule.
2. Paystub fallback requires the stub gross to match the source amount within 1% on BOTH paths (plan: employer match OR gross+frequency match), so an old stub from before a raise is never used.
3. `clearingLagFor` is internal (`clearingLagOf` in `lib/recurring-detect.ts`) and surfaced as `DetectResult.clearing`, tested through `detectRecurring`; for a record tied to a budget category the lag uses that tag's payments from ANY account. Reason (live): Solar is recorded on the Heating & Electric envelope account but paid from Primary Checking, so the existing account-strict `matchRows` finds no history for it. The late flag keeps the strict match.
4. Ledger month dating is built in `itemsFor` (`budgetDatedEvents`, one shape per month) rather than a month restriction on `Shape.payloads`; same result, smaller diff.
5. `expandShape` calls the wrapper with an empty index and `getEnvelopeSummary` reads incomes through the loader, only so the guard test can be strict (the plan's allow-list named fewer files). The guard scans the whole repo (`app`, `lib`, `actions`, `components`) with a 5-file allow-list instead of only the listed consumers.
6. Deposits query also filters `pending: false`; stubs are filtered per source entity.
7. The clearing note also attaches to a bill whose budget and record days agree ("Usually clears about the 3rd." on the Mortgage, live), not only to the day-mismatch line.
8. `hasResolvableDay` helper added to keep "no resolvable date => no reminder" without changing weekly/biweekly defaults.
9. Live Eric take-home is $6,064.87 (plan: 6,064.86): two newer deposits moved the median of the last 6 by a cent.
