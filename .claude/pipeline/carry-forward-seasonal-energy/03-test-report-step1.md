## Acceptance criteria (the 8 items in the brief; plan section 9 for Step 1)

1. **Resolver rules: PASS.** Own row wins; else latest EARLIER row of the same entity+tag; carries amount/payDay/frequency/payDayOfWeek/biweeklyAnchorDate/payMonth/annualAmountDue (+ the rollover FLAG, display only); `rolloverAmount` -> null and `additionalAmountCents` -> 0; `budgeted: null` stays null; synthetic id `carried:<srcId>:<period>`; never from a later row, never backwards. Evidence: my independent oracle (no shared code: indexes by `entity|tag|ordinal`, steps backwards one month at a time, decides "ended" by a lookup at the entity's max ordinal) agrees on 4000 seeded random worlds (1-3 entities, 1-6 tags, gaps, ended lines, variable lines, invalid periods, far-future outliers, shuffled input, 30-month span crossing 2026/2027/2028), comparing source, carriedFrom, period, every copied field, ids, order. The fuzz asserts each branch fired >50 times (own, carried, ended-skipped, variable-skipped, gap-carried, backward-skipped, year-boundary, outlier). Independence-of-requested-window property (300 worlds): resolving 24 months at once equals resolving each month alone. Input rows are not mutated.
2. **Ended-line guard: PASS.** A line carries only if it has a row in its entity's latest budgeted month (per entity); a line present in the frontier but missing in a gap month carries into the gap from the row before it; a line not in the frontier never carries (including into a gap before its last row). **Frontier hazard reproduced and documented (see D1):** one row for a far-future month (or just the first real 2027-01 row of one line) makes every other line of that entity stop carrying into ANY month after its own last row, even 2027-01; tests `TESTER: the frontier hazard is real and documented` pin all four shapes (outlier, first-row-of-new-year, per-entity isolation).

## Defects and findings (none blocking)

**D1 (medium, design consequence, owner decision; NOT a code defect, follows owner answer 1).** The frontier is the entity's latest month with ANY row. Repro (test `the first real row of a new year ...`): rows A, B in 2026-12; add ONE row C in 2027-01 -> resolving 2027-01..02 returns only C; A and B vanish from 2027-01 onward, because they are not in the new frontier. In real use this triggers the first time the owner adds a single line on `/budgets` for 2027-01 (the page is empty for that month and has no copy-forward button): every other Personal line disappears from the Forecast, ledger, pace, notifications and the assistant for 2027-01 and later until all are re-added. Same for a stray far-future row. Expected (per the Coder's open item): documented; actual consequence is stronger than "lines stop carrying beyond their own last row". Recommend the "Copy last month's lines" button (or deriving the frontier only from months up to the requested month plus a one-month look-ahead) before 2027-01.

**D2 (low, unreported side effects today).** The implementation note says the EKC change is "the one place the Forecast page changes today". EKC carrying (single curated month 2026-09) also changes, TODAY: (a) `get_budget_status` for 2026-10 returns 66 rows instead of 56 (10 EKC rows with `carried_from 2026-09`), and the assistant overview lists them and adds them to "Total budgeted"; (b) the recurring-budget hint; (c) **notifications**: `checkBudgetOverspend('2026-10')` now iterates the 10 carried EKC rows. Read-only calc against live October spend: EKC "Utilities" spent 361.06 vs carried budget 200 (180%) so the next overspend cron run would create a "Budget alert: Utilities" for EK Consulting; "Software Subscriptions" 43.63 of 75 (58%, no alert). The business forecast shows $100/month, not ten itemised lines (see live section). All follow from the rule the owner asked for, but the owner should know an alert will start appearing for a month he never budgeted on EKC. Cron safety itself is fine (rejects on read error as before).

**D3 (low).** The Coder's guard regex `\b(?:db|tx|prisma)\.budget\.\w+` misses 7 of 10 access forms (list in criterion 5). Covered by my broader scanner; the Coder's `CONSUMERS` check also only requires the loader name to appear in the file text.

**D4 (info).** Loader cost: 2-3 sequential round trips per call (Budget rows, the relation sub-queries, then the AppSetting read, which could run in parallel with the Budget read) and the Forecast page calls it about 3-4 times per request. Today 681 rows; fine in production, about 1.1 s per call from a laptop with 480 ms RTT. A request-scoped cache is the follow-up if it matters.

**D5 (info).** `loadEffectiveBudgetRowsSafe` has no production caller (it is tested). A failed AppSetting read silently falls back to the default variable set (no setting UI exists yet, so no effect today; once Step 2 adds one, a transient read error would flip an owner-customised set for that request).

**D6 (info).** Advisor `loadBudgetFacts` now sorts in JS (code-unit order) instead of the DB's `orderBy`; with 66 rows and a 400 cap no visible difference, but ordering of names differing only by case/punctuation can differ from the Budgets page.

Pre-existing, noted only: `scripts/validate-imports.ts` / `scripts/import-budgets.ts` read Budget directly (dev tools, not scanned by the guards).
