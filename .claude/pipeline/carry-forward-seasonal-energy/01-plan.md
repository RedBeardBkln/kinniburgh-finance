## 4. Part 1: carry-forward (step 1, no migration)
### 4.1 Rule (pure, `lib/budget-carry-forward.ts`)
`resolveBudgetRows(allRows, period, opts)`: for each (entityId, tagId): own row for `period` wins (`source:"own"`); else the latest row with `period' < period` (`source:"carried"`, `carriedFrom: period'`); never from a later period; never backwards before the first row. Copied: budgeted (null stays null = auto-sum), accountId, payDay, frequency, payDayOfWeek, biweeklyAnchorDate, payMonth, annualAmountDue. NOT carried: `rolloverAmount` (computed, becomes 0), `additionalAmountCents` (looks one-off: 2026-07 only), `id` (synthetic `carried:<srcId>:<period>`; carried rows are read-only views and no action may receive them). Rollover flag copied for display only.
Ended-line guard (R1): a line carries only if it also exists in the entity's frontier period (the entity's latest period that has any rows). A line absent from the frontier is treated as ended and is not carried into later months. Without this rule, deleting a finished bill from the last month would bring it back forever, and the app has no other way to end a line.
Variable set: `AppSetting` key `seasonal_budget_lines` = JSON `[{entityId, tagId}]`, cap 20; absent = default resolved by tag name for the Personal entity: `Utilities / Electric (Eversource)`, `Utilities / Oil`, `Utilities / Firewood`. A variable line still carries its flat amount forward (it is the fallback); the flag `variable:true` tells consumers to ask the seasonal estimate first. Owner edits the set from the Forecast "Seasonal lines" card (step 2); until then the default applies.
### 4.2 Loader (read-only, fail-soft, `lib/budget-carry-forward-build.ts`)
`loadEffectiveBudgetRows({ periods, entityId?, select })` : one `db.budget.findMany({ where: { period: { lte: maxPeriod } }, select: explicit, take: 5000 })` (about 650 rows today), resolved in memory per requested period. On error returns own-rows-only behaviour via `{ rows: [], failed: true }` and logs `err.name`. `loadBudgetScheduleIndex` (lib/bill-dates-build.ts) is extended to fill carried entries so `effectiveSchedule` needs no change except a `carriedFrom` field in its result.

## 5. Part 2: seasonal model
### 5.1 Contract (pure, `lib/seasonal/*.ts`, no DB, no clock)
`seasonalEstimate(input) -> { status:"estimate", month, amount, low, high, confidence:"low"|"medium"|"high", basis:string, observed:number[] } | { status:"gated", reason:string }`. Gate returns a reason, never a number; consumers then use the carried flat budget and print the reason once.
Electric profile: group months into heating (Nov-Mar) and non-heating (Apr-Oct); month estimate = shrinkage: (n_m x mean_m + 1 x group_mean) / (n_m + 1), with `k=1` fixed and documented; low/high = lowest/highest observed bill in the same group ("range of your own bills in that season"), widened by nothing invented.
Gates: v0 (dollars from transactions) needs at least 6 distinct observed calendar months, at least 2 in each group, newest within 90 days; else gated. Confidence: low when any month has 1 observation (true today), medium with 12-23 consecutive months, high with 24+ and every month seen at least twice. Missing months are unobserved, never 0. Months older than 36 are ignored.
v1 (with upload): profile in kWh by calendar month x recent price per kWh = trailing 3 bills total $ / total kWh; if an exported/solar-credit field exists, price uses net bill $ (see R3). Oil: gallons by month profile x owner $/gal. Firewood: units per season x recent $/unit.
Lumpy lines (oil, firewood): model ONE 12-month cost-of-use table (accrual view, used for the table and Pace) and, for cash-flow events, delivery events: walk months accumulating predicted gallons since the last delivery; when the total reaches the median historical delivery size (tank size if the owner gives it) emit one delivery on the 15th of that month, amount = gallons x current price, labelled estimate. Needs at least 2 observed delivery pairs in v1; v0 does not do this.
Oil v0 (no gallons): NO monthly estimate and no replacement of draws. It shows (a) trailing-12-month McCarthy spend, optionally price-adjusted: each payment x P_now / P(date), P(date) = latest owner price effective on or before the payment, payments with no earlier price excluded and counted; (b) implied gallons = sum(amount / P(date)) (labelled "implied, includes any service charges") and sensitivity "each +$0.50/gal adds about $X over the last 12 months of use". Both need >= 2 owner price entries >= 6 months apart; otherwise the card says what to enter. Reads Personal entity only by default; payments in another bucket (the EK Consulting card above) are listed and included only if the owner ticks "include" (answers Q1).
Firewood v0: gated (2 purchases, 1 season); shows the two payments and the carried budget.
### 5.2 Interaction with accrual draws and ScheduledBill (no double count)
Never writes AccrualDraw/ScheduledBill/Budget. Precedence per window: hand-entered draws win where they exist. The model fills only dates AFTER the last hand draw (fixes the empty tail after 2027-04) and, for Electric (static bill), replaces the flat monthly amount in the `generateBillOccurrencesBudgetDated` wrapper via a new optional `amountByPeriod` map; `generateBillOccurrences` and `lib/forecast.ts` stay untouched. Owner opt-in `AppSetting seasonal_replace_draws` (default false) makes the model replace hand draws in forecasts only (draws stay in the DB). A draw dated in the past (the 10-02 oil $2,000) is ignored by the generator already; the Forecast card shows entered draws next to the estimate so the owner can prune them. This changes the module invariant "amount is always the bill's" in `lib/bill-dates.ts`: update its header, `bill-dates.test.ts` and `net-income-guard.test.ts` accordingly.
### 5.3 Oil price input (step 2, no migration)
`AppSetting oil_price_history` JSON `[{effectiveOn:"YYYY-MM-DD", pricePerGal:"3.4990", note?:string<=120, removed?:true}]`, cap 60; price as a decimal STRING (Decimal at runtime), >0 and <=20, 2-4 decimals, date not >30 days in the future; "remove" sets `removed:true` (kept). Action `actions/seasonal-settings.ts` starts with `requireAuth()`, last write wins (single owner; documented); log ids/counts only (no price or note values). Fail-soft: unreadable setting means no price, not 0.

## 9. Acceptance criteria
- Resolver: own > carried > none; never later/backwards; frontier guard; cross-year carry (2026-12 -> 2028-02); synthetic ids; rollover/additional not carried; null `budgeted` preserved.

- "No budget line for <period>" appears only when nothing exists to carry; carried note shows the source period.
- Seasonal output always carries `basis` and `confidence`; gated returns a reason and no amount; flat budget stays when gated; no estimate when fewer than the gate's data; nothing shows 0 for an unobserved month.
- Hand draws still drive oil/firewood events inside their range; model events only after the last draw; no month has both for the same line; replace-draws is off by default.
- Oil price validation (<=0, >20, 5 decimals, bad date rejected); removed entries kept; sensitivity text only with >= 2 prices >= 6 months apart.
- Entity separation: a Personal estimate reads only Personal rows unless "include other bucket" is ticked; SV lines excluded unless added to the setting.
- Every action starts with `requireAuth()`; no AuditLog values/reasons, ids and counts only; no account numbers in UI/logs; upload preview never saves unchecked rows; duplicates blocked.
- `pnpm typecheck`, `pnpm lint` (52 warnings, 0 errors baseline) and `pnpm test` (baseline 455 files, 12,614 passed, 11 skipped) green, also with `DATABASE_URL` pointing at a dead host.
