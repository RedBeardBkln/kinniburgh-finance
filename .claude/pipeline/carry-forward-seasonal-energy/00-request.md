# Task Request: carry-forward-seasonal-energy

## Owner statements (2026-10-09, verbatim)
"All budgeted bills and expenses should carry forward, as budgeted, month to month, regardless of the year. The only budgeted bills that change are electric (Eversource), oil (McCarthy), and firewood. There is a pretty wide seasonal swing with the electric and oil so if you build the feature I can upload a history of the electric, oil and firewood consumption so the system can factor in a more accurate monthly prediction that covers the entire year. On the forecast page I should also be able to enter the cost per gallon of heating oil to better help the forecasting model, since the cost has gone up so much in the past year."

## Part 1: Carry-forward of budgets (small, do first, no migration)
- Budget rows exist per period (YYYY-MM) and currently only for 2026-09..2026-12. For ANY month without a Budget row for an entity+tag, the effective budget (amount, payDay, frequency, payDayOfWeek, biweeklyAnchorDate, payMonth, annualAmountDue) is the most recent earlier row for that same entity+tag (carry forward, any number of months/years). Exception: the three variable lines (Electric (Eversource), Oil, Firewood, identified by tag per entity; make the set of "variable" tags an explicit, owner-editable setting, default = those three) do NOT carry a flat amount forward: they use the seasonal model in Part 2 (their budgeted figure remains the fallback until the model has enough data).
- One shared pure resolver (e.g. `lib/budget-carry-forward.ts`) + read-only loader used by every consumer that currently reads Budget rows for forward months: the budget-date helper (`lib/bill-dates*.ts`, which today falls back to the bill record when a month has no row and prints "No budget line for <period>"), the business-bucket forecast (`app/forecast/page.tsx` touchedPeriods/`lib/business-forecast.ts` uses Budget rows per period), the Upcoming ledger input, the Category Spend Pace, advisor tools that read budgets, and any notification that uses Budget amounts. Remove/adjust the "No budget line for <period>" note where carry-forward now applies (keep a quiet note that the figure is carried forward from <period>). Do NOT create Budget rows or write to the DB; this is a read-time rule. Check how the /budgets page treats a new, empty month (copy-forward or blank) and report; do not change /budgets behavior unless the plan justifies it.
- Nesting/auto-sum, rollover and recurring-expense override logic on /budgets must be unaffected.

## Part 2: Seasonal prediction for Electric (Eversource), Oil (McCarthy), Firewood
Goal: a month-by-month prediction for the next 12+ months for these three lines, used by the cash-flow forecast, the Upcoming ledger, Category Spend Pace targets (projected month cost), and the advisor, replacing the flat budget figure ONLY when there is enough history; always labelled as an estimate with its basis; never fabricated.
Data sources (design for all, ship in this order of value):
1. EXISTING transactions (read-only): Eversource payments on Primary Checking since 2025-05 (swings $41 to $665 per bill), McCarthy oil payments, firewood purchases. Determine from live data how complete/usable these already are (payee strings, tags, amounts, dates, deliveries per season). Also the existing `AccrualEnvelope`/`AccrualDraw` oil/firewood draws (estimated Dec 16 oil ~$2,000, Dec 14 firewood ~$315 currently) and `ScheduledBill` rows (amountType accrued/fluctuating): decide how the model relates to them (generate/replace estimated draws? must not double count with the draws the owner entered by hand; draws entered by hand win unless the owner opts in).
2. OWNER UPLOAD of consumption history: electric (kWh and $ per billing period; Eversource usage export is likely CSV/Excel, or PDF bills), oil (delivery date, gallons, $/gal, total), firewood (date, cords/quantity, $). Needs a new upload UI on the Forecast page (or Budgets) with: CSV/XLSX parsing with a column mapper the owner confirms (never silently guess columns), manual row entry/edit/delete, preview before saving, duplicate protection (same period/date + quantity), per-kind units (kWh, gal, cord/other), and for PDFs/images optionally reuse the existing document-extraction pipeline (`lib/doc-extract.ts`) if it fits; the Planner decides the v1 scope and states what the owner should upload first. History is financial data: auth on every action, no account numbers, archive-not-delete for imported rows (append-only mindset), audit log ids/counts only.
3. OWNER INPUT of heating-oil cost per gallon on the Forecast page: current $/gal (+ effective date, optional note), with a short price history list so the model can show the effect (price is up a lot over the past year). Simple inline form; fail-soft; persisted without a migration if reasonable (e.g. via the existing `AppSetting` JSON pattern used by recurring dismissals) or as part of the new table; validate (> 0, sane upper bound, 2-4 decimals).
Model (the Planner designs and justifies with a backtest on the available data, honest about sample size):
- Monthly consumption profile by calendar month (kWh, gallons, cords) from history (median/mean of the same month across years; with <12 months of data say so and shrink toward the flat budget; never extrapolate seasonality from fewer than the minimum data it needs).
- Cost = predicted consumption x price: oil price = owner-entered $/gal (latest), electric price = recent effective $/kWh from the history/bills (delivery+supply), firewood = recent $ per unit. Show the sensitivity (e.g. "each +$0.50/gal adds about $X over the winter") if cheap.
- Oil/firewood are LUMPY (deliveries). Decide whether to model monthly consumption cost (accrual-style) vs predicted delivery dates/amounts (requires tank size / typical delivery size: ask the owner; default = use historical delivery sizes and cadence). Keep the existing accrual-draw mechanism consistent.
- Output a 12-month table per entity/tag with the prediction, a range, the confidence and "why", and use it where the flat budget was used before.

## Constraints
- Ground rules: never fabricate (estimates labelled with basis; gates return a reason, not a number), observational wording, no advice, entity separation, Decimal money, UTC stored / NY displayed (`formatCalendarDate` for date-only), `requireAuth()` first in every action, loaders read-only with explicit selects and fail-soft, no account numbers in UI/logs, preserve LF/CRLF with binary edits.
- Schema: Part 1 needs NO migration. Part 2 history storage most likely needs one new additive table (e.g. `UtilityUsage`: entityId, tagId or kind, periodStart/periodEnd or deliveryDate, quantity, unit, costCents, unitPriceCents?, source, importBatchId, archivedAt, createdAt) per the repo's additive-only schema policy. The Planner must (a) design it, (b) provide a no-migration fallback for v1 if one exists (e.g. AppSetting JSON capped), (c) flag clearly that pushing a migration deploys it (build runs `prisma migrate deploy`; there is no shadow DB) so the owner must OK before any push containing it. Agents must NOT run migrations or `prisma generate`; write the migration SQL by hand following the repo's migration folder convention and flag it.
- Keep the build split into independently shippable steps: (1) carry-forward (no migration), (2) oil price input + model v0 from EXISTING transactions (no migration if AppSetting), (3) upload/history table + model v1 (migration). Say which step the owner would see first.
- Read-only live checks via a temporary repo-root script (`node_modules/.bin/tsx --env-file=.env ./_x.ts`, delete afterwards; payee names/amounts/dates only). No DB writes, no tax code.
- Token-frugal.
