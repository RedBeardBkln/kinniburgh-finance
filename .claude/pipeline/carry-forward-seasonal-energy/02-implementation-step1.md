## Summary of changes

New
- `lib/budget-carry-forward.ts` (pure; no db, clock or Next imports). `resolveBudgetRows(allRows, periods, { variableKeys })`: per (entityId, tagId) line: an own row for the period wins (`source: "own"`); else the latest EARLIER row of that line is copied (`source: "carried"`, `carriedFrom`), never from a later period, never backwards before the line's first row. Copied: `budgeted` (null stays null = auto-sum), accountId, payDay, frequency, payDayOfWeek, biweeklyAnchorDate, payMonth, annualAmountDue, rolloverEnabled (flag only). NOT carried: `rolloverAmount` (-> null), `additionalAmountCents` (-> 0), `id` (synthetic `carried:<sourceId>:<period>`). Ended-line guard: a line carries only if it has a row in its entity's FRONTIER (the entity's latest period that has any rows; per entity). Variable lines return their own rows (flagged `variable: true`) and never carry. Also: `parseSeasonalLinesSetting` (AppSetting `seasonal_budget_lines`, JSON `[{entityId, tagId}]`, cap 20, garbage/absent = null = default), `variableLineKeys`, `DEFAULT_SEASONAL_TAG_PATHS`, `carriedNote`.
- `lib/budget-carry-forward-build.ts` (read-only). `loadEffectiveBudgetRows({ periods, entityId? })` (throws on a Budget read error, like the consumers that already propagated it), `loadEffectiveBudgetRowsSafe` (never rejects, `{ rows: [], failed: true }`, logs `err.name` only) and `loadEffectiveScheduleRows` (schedule-only select for the date index). One explicit-select `findMany` of the Budget table (no period filter, `orderBy period desc`, `take: 5000`; about 650 rows live) plus one `appSetting.findUnique` of the setting (an unreadable/garbage setting silently falls back to the default set). No `include`, no write verb.

## Decisions / deviations from the plan (all flagged)
1. The loader has NO upper period bound (plan: `period <= maxPeriod`). Reason: the ended-line frontier is the entity's real latest period; a window that ends before it would otherwise misjudge a line with a gap month. Cost: about 650 rows per call.
2. Three loader entry points instead of one fail-soft one: strict `loadEffectiveBudgetRows` (consumers that already propagated a Budget read error keep doing so, so an outage never silently shows "no budget lines"), `...Safe`, and the schedule-only `loadEffectiveScheduleRows` for the date index (keeps "no amounts" in its select: only `annualAmountDue`; the extra `id` and `tag { name }` are for the synthetic id and the default-variable recognition).
3. Default variable set (when the setting is absent) is by full tag path and applies to whichever entity has a row for it: `Utilities / Electric (Eversource)`, `Utilities / Oil`, `Utilities / Firewood` (Personal) AND `Arbor Retreat / Electricity`, `Arbor Retreat / Oil` (Sudden Valley, owner answer 5: same feature, per entity). Including the two SV lines is my reading of answer 5; remove them from `DEFAULT_SEASONAL_TAG_PATHS` if SV should carry flat until step 2. There is no UI to edit the setting yet (the Forecast "Seasonal lines" card is step 2); until then only the default applies (or a hand-written AppSetting).
4. The assistant's `get_budget_status` note says Electric/oil/firewood lines "are not carried yet" (true until step 2; update the text then).
5. Existing pinned tests changed (8 tests in 5 files, all assertions on the OLD query shape of Budget reads, which this feature must change; no behaviour assertion was weakened):
   - `net-income-consumers.test.ts` (2): the index read no longer filters `where.period.in` (now no `where`, the resolver applies the window) and its select gained `id` and `tag { name }`; the "builds the index" case now also asserts a carried 2026-11 entry.
   - `net-income-budget-dates-tester-consumers.test.ts` (1): same select pin (still asserts no `budgeted`).
   - `recurring-budget-hint.test.tsx` (3 + source scan), `recurring-followups-tester-budget.test.ts` (2), `recurring-followups-tester-pages.test.ts` (1): the hint loader's Budget read is now the shared loader (mock rows gained `period`/`id`; `where` pins changed to the loader's entity-only/none; direct `findMany` / `select:` counts 3 -> 2; the "UTC month" case is now proved through the output instead of `where.period`).
6. Reading of "ended": a line that is in the frontier but has a gap month is carried into the gap (its last row is in the frontier); a line NOT in the frontier is never carried, including into a gap month before its last row. Documented in the resolver test ("gap months").

If someone adds a single line to a far-future month (for example 2027-06) every other line of that entity stops carrying into later months than its own last row, because the frontier moved. The rule follows the owner's answer; the `/budgets` "copy last month" button (recommended follow-up) would make this safe.
