# 02 — Implementation: DB-wiring layer for the tax computation engine (TY2025)

## Summary of changes

**`lib/tax-compute-build.ts`** (new) — the DB-wiring layer described by the plan's "Design" section, implemented function-for-function against the plan's stated signatures:

- `classifyTaxBreakdownLabel` / `classifyAdditionalWithholdingLabel` — the two paystub label classifiers, exact regex logic from the plan, verified against both real live paystubs' label text in tests.
- `sumPaystubWithholding(paystubs, taxYear)` — filters to `extractStatus === "complete" && payDate` in `taxYear`; sums `taxBreakdown`/`additionalWithholding` by classified bucket; unrecognized labels go to `unrecognizedLabels`, never silently summed or dropped.
- `findUnparseableExtractions(documents)` — flags any complete-status document whose `extractionData.summary` is the exact literal string `doc-extract.ts#parseExtractionResponse`'s catch branch produces.
- `sumW2Documents(documents, taxYear)` — sums `wagesCents`/`medicareWagesCents`/`federalWithheldCents`, and `stateWithheldCents` into `ctWithheldCents` (documented CT-only assumption inherited from `lib/tax-form-plan.ts`); a doc with no numeric `wagesCents` goes to `unusableDocs`, never counted as `$0`.
- `sum1099InterestIncome(documents, taxYear)` — only `formVariant === "1099-INT"` counts; anything else (e.g. `1099-DIV`) goes to `excludedNonInterestDocs`.
- `sumItemizedDocInputs(documents, taxYear)` — sums `mortgage_interest` docs' `interestCents`; `property_tax` is always `$0` (the extraction shape never yields a number); both branches always push a distinguishing note.
- `parseDollarAnswerToCents` / `parseSqftAnswer` — strict-regex free-text parsers; `skippedReason !== null` or empty/null answer → `{value: null, unparseable: false}` (genuinely unanswered); anything else that doesn't match the regex → `unparseable: true`. Never guesses at prose.
- `resolveHomeOfficeSqft` — only returns non-null sqft when eligibility is `"yes_exclusive"` AND the sqft answer parses; a stray sqft answer under any other eligibility value is ignored with an explanatory note.
- `resolvePersonalTaxComputeInput(raw)` — pure top-level resolver. Wires every sub-resolver above into the exact `ComputePersonalTaxReturnInput` shape `lib/tax-compute.ts#computePersonalTaxReturn` requires; builds `buildGaps` by inspecting what each sub-resolver actually returned (never a static list); sets `scheduleCDataMissing: true` whenever both EK Consulting GL totals are zero, with the plan's exact high-priority message.
- `buildPersonalTaxComputeInput(taxYear)` — the one DB-aware export (imports `db`, `getEntityBySlug`, `computePL`). Mirrors `app/tax/personal/[year]/page.tsx`'s existing query shapes: `getEntityBySlug("personal")` / `getEntityBySlug("ek-consulting")`, `db.document.findMany`, `db.paystub.findMany`, `db.taxWorkspace.findUnique` → `db.taxQuestion.findMany` (or `[]` + a gap note if no workspace exists yet), `db.mileageEntry.findMany` + `computePL` for EK Consulting (or `[]`/`Decimal(0)` + a gap note if the entity lookup fails). Calls `resolvePersonalTaxComputeInput` and returns its result, with orchestrator-level gaps prepended. Not unit-tested, per plan and repo convention.

**`lib/__tests__/tax-compute-build.test.ts`** (new) — 38 tests covering every pure function per the plan's "Test expectations" section: both paystub-label classifiers against real live label text (including the confirmed CT-label variance and the `"Local Tax"`/unrecognized case); `sumPaystubWithholding` with fixtures shaped exactly like the two real paystubs; `findUnparseableExtractions`'s three pinned cases (flagged, normal W2 not flagged, `extractionStatus !== "complete"` not flagged); `sumW2Documents` (valid sum, wrong-year exclusion, incomplete-status exclusion, mistagged-1098-shape → `unusableDocs`); `sum1099InterestIncome` (INT summed, DIV excluded, wrong-year excluded); `sumItemizedDocInputs` (0-doc and populated cases for both `mortgage_interest`/`property_tax`); `parseDollarAnswerToCents`/`parseSqftAnswer` (all plan-specified cases including the real live `"skipped"`/`"Skipped for now"` shape and the `"Yes"`-is-unparseable case); `resolveHomeOfficeSqft` (all 4 plan-specified cases); and an end-to-end `resolvePersonalTaxComputeInput` test built from a fixture mirroring the real live data shapes (2 valid W2s + 1 unusable/mistagged W2 + 1 `1099-INT` + 1 `1099-DIV`, zero mileage, zero mortgage/property-tax docs, narrative-only tax questions, zero EK Consulting GL totals), asserting every gap the plan named plus `scheduleCDataMissing === true`; a second fixture with `home_office_sqft` answered and nonzero GL totals asserting `scheduleCDataMissing === false` and the high-priority message's absence; a third test confirming an unparseable `estimated_tax_payments_amount` answer is flagged as unparseable (not silently treated as unanswered).

**`lib/tax-guidance.ts`** — added exactly 3 new `TAX_QUESTION_BANK` entries, each free-text (`options: undefined`), placed immediately after their narrative counterparts:
- `home_office_sqft` (category `deductions`, unlocks `["home_office"]`) — placeholder `"e.g. 180 (whole square feet, no unit needed)"`.
- `retirement_contribution_amount` (category `deductions`, unlocks `["retirement_savings_credit", "ira_deduction", "hsa"]`) — placeholder `"e.g. 12000 (whole dollars, no $ sign needed)"`.
- `estimated_tax_payments_amount` (category `other`, unlocks `["safe_harbor"]`) — placeholder `"e.g. 8000 (whole dollars, no $ sign needed)"`.
No existing entry was touched — confirmed via `git diff` showing zero removed/changed lines, only additions.

**`actions/tax-planning.ts`** — `ensurePersonalWorkspace`'s existing-workspace branch: removed the `if (existing.questions.length === 0)` guard around the seeding `createMany` call. It now always attempts the `skipDuplicates: true` createMany for an existing workspace. This is a real, if small, behavior change (flagged explicitly per the plan's own instruction): previously a workspace only ever got seeded once, at first creation; now every call to `ensurePersonalWorkspace` (i.e. every time `/tax/personal/[year]` is opened) attempts to backfill any `TAX_QUESTION_BANK` key the workspace doesn't already have. Safe/idempotent because `@@unique([workspaceId, key])` + `skipDuplicates: true` mean it can only ever add missing keys, never touch or overwrite an already-answered row — confirmed by reading the constraint directly, not assumed.
