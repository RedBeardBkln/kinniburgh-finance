# Task Request: budget-auto-carry-ui (automatic carry-forward on /budgets, no "copy" button)

## Owner statements (2026-10-10, verbatim)
"Why does there need to be a 'Copy last month's lines' button? The budgeted bills and expenses should automatically carry forward month to month, regardless of whether it's December to January or October to November. Whatever is listed in the budget is what should be used to forecast forward. The only adjustments that would be made are to the three utilities we've been discussing (Electric, heating oil and firewood) but those are seasonal and not impacted by a December to January transition."
Then: "Yes, plan it that way" (to the approach below).

## Background (already built and live, read first)
- `lib/budget-carry-forward.ts` (pure resolver) + `lib/budget-carry-forward-build.ts` (read-only loader): forecasts, ledger, assistant, spend pace and two budget notifications already read the EFFECTIVE budget: a month's own row wins, else the latest earlier row of the same entity+tag carries (amount and schedule fields, NOT rollover or the one-off additional amount). An ENDED line (absent from the entity's latest budgeted month; the "frontier" is per entity) does not carry (owner answer 1, 2026-10-09). The variable lines (Electric (Eversource), Oil, Firewood; Sudden Valley Electricity/Oil; AppSetting `seasonal_budget_lines`) carry their flat budget as the fallback until a seasonal estimate passes its gate (`carryVariable: true`).
- The HAZARD: `/budgets` (app/budgets/page.tsx, components/budgets/*, actions/budgets.ts) still shows real rows only; adding a single line to an empty future month (say 2027-01) makes that month the entity's frontier containing only that line, so every other line is treated as ended and stops carrying from that month onward. Also the dashboard, monthly review and the budget CSV export still read real rows only, so a new month (e.g. January) with no rows shows no budgets there even though the forecast carries them.
- The approach the owner approved: NO button. (1) `/budgets` shows the carried lines for any empty month (and for lines missing from a partly filled month, if the resolver says they carry), clearly marked "carried from <period>", so what the owner sees equals what the forecast uses. (2) The first time the owner adds or edits anything in that month, the page saves the full carried set as real rows for that month in the same step (copy-on-first-edit), so the entity's "latest month" is always complete. (3) Deleting a line in a month is how the owner ends it (the rule from answer 1) - think through exactly what delete means for a carried line and for a line that also exists in later months.
- Related code: `lib/budget-effective.ts` (dashboard/budgets recurring override + `resolveEffectiveBudgets`), `lib/dashboard-budget-tree.ts`, `lib/month-spend*.ts`, `lib/budget-nesting.ts`, `lib/budget-pace.ts`, `lib/monthly-review-build.ts`, the budget CSV export (find it), `actions/budgets.ts` (all actions start with requireAuth), the Budget model (unique tagId+entityId+period; accountId required; budgeted nullable = auto-sum parent; additionalAmountCents; payDay/frequency/payDayOfWeek/biweeklyAnchorDate/payMonth/annualAmountDue; rolloverEnabled/rolloverAmount), `lib/__tests__/budget-carry-forward-guard.test.ts` (only allow-listed files may call db.budget.*; carried synthetic ids `carried:<srcId>:<period>` must never reach an action: the new design must change that contract deliberately and safely: e.g. actions receive (entityId, tagId, period) not a synthetic id).

## Required behavior (the Planner designs and justifies; defaults in brackets)
1. `/budgets` effective view: for the selected month (any month from the entity's first budgeted month onward; NOT backward before the first ever row; months past the future horizon: say how far forward [any]) show own rows plus carried rows using the SAME resolver (one source of truth, no second implementation), carried rows visibly marked, read-only until edited or materialized, totals consistent with the forecast, recurring-expense override / nesting / rollover logic unaffected. Entity buckets (Personal, Sudden Valley, EK Consulting) separate.
2. Copy-on-first-edit: every write path on /budgets for month M (add line, edit amount/schedule/account/frequency, change additional amount, toggle rollover, delete, nest/un-nest if applicable, and any bulk edit) first materializes the carried set for M into real rows (carried amount and schedule; rollover and additionalAmount NOT carried; account as carried; variable lines: decide with recommendation whether they are materialized with their flat figure [yes, so /budgets shows them; the seasonal model still replaces the figure in forecasts only when its gate passes]), atomically in one DB transaction with the edit, idempotent under double-click/two tabs (unique key tagId+entityId+period; use createMany skipDuplicates or upsert-by-key semantics; never overwrite a row that already exists), with an AuditLog row of ids and counts only (follow the neighbours), requireAuth first. A carried line is edited by sending (entityId, tagId, period, change) - never a synthetic id.
3. Delete/end semantics: define precisely what deleting a carried (not yet materialized) line and a materialized line does, including a month that is not the entity's latest month, and what the UI says ("This removes the line from <period> and every later month" vs only this month): the owner's rule is that a dropped line stops carrying; propose the clearest rule and its UI wording, with a recommendation, and make the resolver and the UI agree.
4. The other readers: the dashboard (`app/page.tsx` budget lines, Total Budgeted, Overspent Lines), monthly review, budget CSV export and the dashboard spend loaders must use the effective rows for months that have no rows of their own (so Jan 1 shows the carried budget instead of $0/"no budgets"), via the shared loader; define behavior for PAST months (use real rows only? carried rows for a past month that never had rows? recommend). Keep the dashboard reconciliation invariants (Total Budgeted equals /budgets for the same month; Spent unchanged).
5. Remove the 'frontier hazard' note in CLAUDE.md once solved; keep guard tests (update the guard allow-list deliberately with reasons); the ended-line guard stays as the owner's rule.
6. Do NOT migrate or change the schema. No data backfill script: nothing is written until the owner edits a month in the UI. All writes through real server actions.
