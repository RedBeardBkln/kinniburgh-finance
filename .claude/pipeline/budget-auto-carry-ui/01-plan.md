## 1. Restated goal
Make what the owner SEES on /budgets (and the dashboard, monthly review and CSV) equal what the forecast already USES: for any month with no row, show the carried lines (marked "carried from <period>"), with no copy button. The first write in such a month saves the full carried set as real rows in the same transaction, so the entity's latest month is always complete and the "frontier hazard" disappears. Deleting a line ends it from that month on.

## 4. Design

### 4.1 Effective view on /budgets (one source of truth)
- Page loads `loadEffectiveBudgetRows({ periods: [period] })` once WITHOUT entityId (all entities; the frontier is per entity anyway), then splits in memory: the selected bucket's rows for the table and all rows for the tag-used list (`budgetedTagIdsAllEntities` = tag ids of every effective row of the period, own or carried). This removes both direct `db.budget` reads from the page.
- Loader select gains `account: { select: { nickname: true, entity: { select: { name: true } } } }` (label fields only; no balance/mask). The page fetches balances for the annual-reserve alert by one `db.account.findMany({ where: { id: { in } }, select: { id, currentBalance, currentBalanceAt } })`. The page sorts in memory by account nickname then tag name (the old `orderBy`).
- Everything downstream is untouched: `resolveEffectiveBudgets` (recurring override, auto-sum nesting, roots-only total), `buildMonthSpend`, `computeBudgetSummary`, `assessAnnualFunding`. A carried row is just a row with `rolloverAmount = null` (shows "—"), `additionalAmountCents = 0`. Its synthetic id is only used as a React/Map key; it is never sent to an action.
- `SerializedBudgetLine` gains `entityId`, `source: "own" | "carried"`, `carriedFrom: string | null`. A carried row shows a quiet second line under the category: `Carried from December 2026` (use `formatPeriod`), and, when the month has any carried row, one muted banner above the totals: "This month has no saved budget of its own yet. The lines below are copied from {Dec 2026} and are what the forecast uses. The first time you change something here, the whole list is saved for this month." Edit and Delete stay enabled on carried rows (no read-only state to explain). No button.
- Months: no backward carry (resolver). Picker options become the last 12 months through the next 12 (crossing years), plus the selected month if outside that window. Any valid period in the URL is rendered; WRITES are refused beyond current NY month + 24 (`"That month is too far ahead to edit yet."`). Entity buckets stay separate (rows keep their own entityId; All-Entities view lists per entity).
- Empty-state text "No budget lines found..." remains only when the effective list is empty (before an entity's first row, Mezzo).

### 4.2 Locator contract (replaces synthetic ids at the action boundary)
`BudgetLocator = { entityId: uuid, tagId: uuid, period: YYYY-MM }` (zod; period regex `^\d{4}-(0[1-9]|1[0-2])$`). New signatures in `actions/budgets.ts` (all start with `requireAuth()`; none accepts a Budget id any more, so `carried:` ids cannot reach them):
`updateBudgetLine(loc, budgeted)`, `updateBudget(loc, input)`, `updateBudgetAdditionalAmount(loc, cents)`, `deleteBudget(loc)`, `createBudget(input)` (already carries entityId/tagId/period). Client changes: `budget-line-editor.tsx` takes the locator; `budget-edit-modal.tsx` edit mode passes it; `budget-page-client.tsx` passes it for delete/additional; `drilldown-dialog.tsx` + `lineEdit` in `lib/dashboard-drill.ts` carry `{entityId, tagId, period}` instead of `budgetId` (dashboard maps `entityId` from the effective row and `period` from the page). Each action looks the row up by the unique key (`tagId_entityId_period`) AFTER materializing.

### 4.3 Materialization (copy-on-first-edit)
New pure `lib/budget-materialize.ts` and DB-aware `lib/budget-materialize-build.ts`.
- `planMaterialization(entityRows, M)` (pure): uses `resolveBudgetRows(entityRows, months, { carryVariable: true })` (a small exported wrapper `resolveEffectiveRows` in the resolver file is used by BOTH the loader and the planner, so the option cannot drift; `variableKeys` is irrelevant when `carryVariable: true`, so the planner needs no AppSetting read) and keeps the `source === "carried"` rows. Months planned = `{M}` ∪ every row-less month from the entity's first row month through `max(M, F)` where F = entity frontier (this covers the gap F+1..M when M > F, and any empty month inside the range). Output create-inputs copy: `budgeted` (null stays null), `accountId`, `payDay`, `frequency`, `payDayOfWeek`, `biweeklyAnchorDate`, `payMonth`, `annualAmountDue`, `rolloverEnabled`; set `additionalAmountCents = 0`, `rolloverAmount = null`. Variable lines (Electric, Oil, Firewood, SV Electricity/Oil) ARE materialized with their flat figure (recommended yes: the page must show them, the forecast already carries them flat, and the seasonal model replaces the figure only in forecast consumers, keyed by line, not by row source). A line already ended is not in the output (ended-line guard untouched).
- `materializeForEdit(tx, loc)`: inside the caller's interactive `db.$transaction(async tx => ..., { timeout })`: (1) `SELECT pg_advisory_xact_lock(hashtext('budget-write'))` via `tx.$executeRaw` (one global lock; two users, tiny traffic; serializes two tabs, the cross-entity tag check and a delete racing a materialize); (2) read ALL Budget rows with the explicit loader-style select (about 700; needed for frontiers and the cross-entity check); (3) plan; (4) `tx.budget.createMany({ data, skipDuplicates: true })` (ON CONFLICT DO NOTHING on the unique key: an existing row is never overwritten, a double click creates 0 the second time); (5) if created > 0, `tx.auditLog.create({ changedBy: user.id, changeType: "budget_materialize", before: JsonNull, after: { entityId, periods, created, skipped } })` (ids and counts only, like the neighbours: `donations.ts` writes AuditLog with `transactionId` null). The action then applies the edit in the same tx.
- Guard against a stale view: the action re-validates against the DB inside the lock; if the line is not in the entity's effective view for M (ended or never existed) it returns `{ error: "That line is no longer on this month's budget. Refresh the page." }` and the transaction rolls back (so a refused edit does not leave materialized rows behind).
- `ScheduledBill` side effects: unchanged and only for the EDITED line (`upsertBudgetBill` as today). Materialized copies do not touch bills (bills are keyed by tag+entity, not period).

### 4.4 Write paths and what each materializes
| Path (UI) | Action | Before the edit | The edit |
|---|---|---|---|
| Inline amount (budgets page, dashboard drill) | `updateBudgetLine(loc, budgeted)` | materialize M | update amount of `(tag, entity, M)` |
| Edit modal (amount, day, account, frequency, weekday, anchor, due month/amount) | `updateBudget(loc, input)` | materialize M | existing logic on the real row; `applyToFuture` pushes schedule fields to existing LATER real rows only (carried-only later months follow automatically because they carry from the latest row); bill upsert as today |
| Additional buffer (recurring lines) | `updateBudgetAdditionalAmount(loc, cents)` | materialize M | set additional on M's row (stays per-month, not carried) |
| Add line | `createBudget(input)` | materialize M | tag conflict check against EFFECTIVE rows of all entities for M (own or carried), then `create`; error text unchanged ("already has a budget line this period" / "...under <Entity> this period") |
| Delete line | `deleteBudget(loc)` | see 4.5 (materialize minus the line, or trim) | end the line from M; bill deactivated as today |
| Rollover toggle, nest/un-nest, bulk edit | none exist (no writer of rolloverEnabled/Amount; nesting is derived from the tag tree; `applyToFuture` is the only multi-row write) | n/a | n/a |
Reads (CSV export, monthly review, dashboard) never write.

### 4.5 Delete = "end the line from this month on" (recommended rule)
Why not "this month only": the resolver carries a line from its latest earlier row whenever the line is in the entity's latest month, so deleting just a middle month's row would make the line reappear as "carried" immediately. The owner's rule is that a dropped line stops carrying, so Delete ends the line.
Algorithm, inside the lock after materializing the fill set (so no other month's effective view changes, invariant I1):
1. M <= F (entity frontier): `deleteMany` rows of (entity, tag) with `period >= M`. Refuse (rollback) if that would leave the entity's frontier month with zero rows (the frontier would move back and revive older ended lines): "This is the only line left in {month}; add another line or remove it from the earlier month."
2. M > F (an empty future month, the line is only carried): materialize M (+ gap) from the carried set EXCLUDING the line; M becomes the frontier without it, so the line has ended for M and later, and months F+1..M-1 keep it as real rows.
3. Always: `scheduledBill.updateMany(... active:false)` exactly as today (kept; limitation in Q4), one AuditLog row `budget_end_line` with `{ entityId, tagId, fromPeriod, deletedRows }` (ids/counts only).
Confirm text (replaces the current `confirm`): `End "{line}" from {Month YYYY} onward? It is removed from {Month YYYY} and every later month, so it stops appearing in the budget and the forecast from then on. Earlier months are not changed. The linked scheduled bill will also be deactivated.` The action returns `{ success: true, removedMonths: n }`; no counts are needed before the confirm.
Resolver and UI agree because the resolver is unchanged: after I1 + the delete, the line's last row is before M, so it is "not in the frontier" and carries nowhere.

Policy for ALL months (past too): the effective view, i.e. own rows, plus carry-forward of lines that exist earlier; never backward before a line's first row. Past months with no rows therefore only fill from an earlier row (live: only EKC from 2026-10; Personal/SV have no empty past month). One rule everywhere keeps Total Budgeted identical across screens. Past months never GET written unless the owner edits them.
- Dashboard `app/page.tsx`: replace the `settle("budget lines", db.budget.findMany(...))` with `settle("budget lines", loadEffectiveBudgetRows({ periods: [period], entityId: entity?.id }))`; map `account.nickname` and `account.entity.name` from the new loader select; add `entityId`, period to `lineEdit`. Same failure behaviour (null = widget unavailable). Keep `auth()` first and the pinned strings in `recurring-followups-tester-pages.test.ts` (check which literal is pinned before touching the line). Visible change today: EKC dashboard shows its 10 carried lines for 2026-10 and later (was "no budgets"). Spent: unchanged (`buildMonthSpend` input shape identical; a carried line claims its tag's spending exactly like a real row).
- Monthly review `lib/monthly-review-build.ts`: both reads (`period`, `priorPeriod`) via `loadEffectiveBudgetRows`; rows keep `tag` and `entity`, which the loader already selects (`tag.shortName/parentId`, `entity.name`). Prior-period forecast accuracy then also covers months that were never saved (EKC); acceptable and consistent.
- CSV `exportBudgetCsv(period)`: effective rows for all entities (same as now). Carried rows get no marker column (header stays; Q6 if wanted). Do not fix the missing recurring override (Q5).
- Advisor, ledger, forecast, notifications, bill dates, recurring hint: no code change. After a materialization their input is identical (I1); only the descriptive note "carried from X" disappears for that month.

### 4.7 Invariants (property-tested)
- I1 Materialization never changes any month's effective view: for every entity and every month in a window, the set of (tag, account, amount, schedule fields, additional, rollover) before == after.
- I2 Idempotent: running it twice creates 0 rows the second time; never updates an existing row.
- I3 After delete(L, M): L absent in every month >= M, every other line and every month < M unchanged, no ended line revived.
- I4 Rollover amount and additional amount are never copied; rolloverEnabled is.
- I5 Entity separation: planning for one entity never reads or writes another's rows (only the cross-entity TAG check reads others).

## 6. Race and idempotency design (summary)
Single interactive transaction per action; global `pg_advisory_xact_lock` first (works under the Supabase pooler because it is transaction-scoped); `createMany skipDuplicates` (DB-enforced uniqueness, no overwrite); edit after materialize by unique key; double click = second call finds rows present, creates 0, applies the same edit; two tabs serialize on the lock; stale view handled by the "no longer on this month's budget" refusal; delete is naturally idempotent (`deleteMany`). If the transaction fails, nothing (neither materialization nor edit) is saved. Known tolerated imprecision: materialization copies the carried values current at click time, not those on screen if another tab edited the source month in between.
