## Summary of changes

## Behavior (what the owner will see)
- `/budgets` for any month: own rows plus carried lines through the shared loader. A carried line reads "Carried from December 2026"; one notice: "This month has no saved budget of its own yet. The lines below are copied from December 2026 and are what the forecast uses. The first time you change something here, the whole list is saved for this month." (a partly filled month says "N of the lines below have no saved row for this month yet ..."). Rollover shows a dash and the additional buffer 0 for a carried line (neither is carried). The empty state "No budget lines found for ..." remains only before an entity's first row (and Mezzo).
- First edit/add/additional/delete in a carried month: one transaction saves the carried set for that month and every empty month up to it, then applies the edit; a second click saves nothing new; a failed edit leaves nothing.
- Delete: ends the line from that month on. Month with rows: the line's rows from that month on are removed (earlier months stay). Month that is only carried: the other lines are saved for the gap months and that month WITHOUT the line, so that month is the new latest month and the line has ended. Refused ("This is the only line left in <Month>; add another line or remove it from the earlier month.") when it would empty the entity's latest month. A second click on a line that is already gone answers success (removedMonths 0) and touches nothing.
- Dashboard, monthly review and CSV show the effective rows for every month (past months too; never before a line's first row). Dashboard Total Budgeted equals /budgets (test renders both pages over the same rows); Spent is unchanged (the spend model input has the same shape; a carried line claims its tag's spending like a real row).

## Deviations from the plan
1. The plan said interactive transactions with an advisory lock had no precedent in the repo. They do: `lockAssignPair` in `lib/review-queue-server.ts` and `actions/review-assignments.ts` (deployed). I used the same pattern (parameterised `hashtext`, `maxWait`/`timeout` options). The plan's array-form fallback was therefore NOT needed. A read-only interactive `$transaction` over the app's real connection (transaction-mode pooler URL with `pgbouncer=true`, from `.env`) worked live. I did NOT acquire the advisory lock live (not a data write, but I kept to "no write of any kind"); the precedent file is what proves it behind this pooler.
2. `planEndLine` also saves the ended line's own gap months (months before the chosen one where the line has no row of its own and is shown only by the carry). Not in the plan: found by the independent oracle test (seed 1: after ending a line, an earlier gap month where the line was shown by the carry vanished once the line left the entity's latest month, violating "nothing earlier changes"). Fixed in the planner and pinned by a unit test and the property test.
3. Two more guard tests encoded the old contract and were changed deliberately: `budget-carry-forward-tester-guard.test.ts` (allow-list, "/budgets never sees carried rows", "no action imports the carry modules") and `dashboard-drill-guard.test.ts` (the dashboard page and /budgets "still read real rows themselves"; client components keep the ban). The plan listed only `budget-carry-forward-guard.test.ts`.
4. Test mocks/fixtures changed (no assertion weakened): `entityId` added to `DrillBudgetRow` fixtures in 5 dashboard test files; `dashboard-accuracy-tester-page.test.tsx` mocks gained `appSetting.findUnique` and rows gained `entityId`/`period`/`tag`; its pinned `where` of the Budget read changed from `{ entityId, period }` to `{ entityId }` (the shared loader reads the entity's rows without a period filter, the frontier needs the later months); the select-key pins in `budget-carry-forward-build.test.ts` and `-tester-consumers.test.ts` gained `account`; the `dashboard-drill.test.ts` `lineEdit` expectation is the locator.
5. Delete of a line that is already gone returns success with `removedMonths: 0` instead of the stale-view error (plan section 6: delete is naturally idempotent; a double click must not show an error).
6. The `BudgetLineLocator` type is exported from `actions/budgets.ts` (type only; legal in a "use server" file) so the inline editor is typed.

### Reconciled planner logic (what is still needed, what is not)
- `planEndLine`: REMOVED the round-0 block "save the ended line's own gap months first": a month that has rows is authoritative, so no month shows a line only by the carry any more. - The refusal rule is GENERALIZED (exposed by the Tester's delete fuzz after the resolver change): ending a line must not leave ANY month that holds rows today with none, because an empty month would start to carry the other lines. Before it protected only the latest month; now a middle month that holds only this line also refuses (same plain message, naming that month), and a target month after the latest one still needs another line. The only way left is an entity-level empty month in which nothing is carried today but the re-added line would be (it has older rows). Refused with "Adding this line here would also make it appear in <Month>, an earlier month that has no budget lines. Add it to that month first, or choose that month instead." and nothing is written. - Ending a line is refused when it would leave any month empty (middle months included). The message names the month; the owner either adds a line to that month or ends the line from the earlier month. No live month triggers it.
- `addChangesEarlierMonth` refuses the rare re-add that would reach into an empty earlier month (an entity-level empty month in which nothing is carried today); nothing live triggers it.
