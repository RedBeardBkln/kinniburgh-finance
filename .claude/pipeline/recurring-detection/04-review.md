## Required changes (blocking)

1. **Exclude unpaired card-payment descriptors on checking (Tester defect 2). `lib/recurring-detect.ts`, `SKIP_PAYEE_RE` (line ~118).** A fixed monthly `capital one mobile pmt`, `barclaycard us payment`, `amex epayment ach pmt` or `crcardpmt` row on a checking account would be offered at HIGH confidence, and "Add as recurring expense" would put the card payment into the counted totals while the same spending is already counted from the card account's own bills/budgets: a straight double count, which is the exact failure the learned block is designed to avoid. Only `card pay` and `creditcard` are covered today. Live data has 11 unpaired `capital one crcardpmt` and 3 `amex epayment` rows that merely happen to be irregular; the household's own card payments are the likeliest thing to become steady (autopay of a fixed amount). Add narrowly, do not add plain `payment`/`paymt` (that would drop real bills such as "enerbank usa acct paymt" and "invoice cloud webpayment"). Suggested tokens: `crcardpmt`, `\bepayment\b`, `\bmobile pmt\b`, `\bcard pmt\b`, `barclaycard`, `\bamex\b`, `american express`. Add a unit test per descriptor (monthly fixed 100.00, six months, checking account, expect no suggestion and no late flag) plus one test that "invoice cloud webpayment" and an "... acct paymt" bill are NOT excluded.
2. **Drop rows whose canonical payee is empty (Tester defect 1). `lib/recurring-detect.ts`, `filterRows` (line ~815).** `canonicalPayee("***")` returns `""`; the series key becomes `E1|A1|out|`, two different punctuation payees merge into one nameless series, and a late flag can start with a blank. Latent on live data (0 rows) but it is a one-line guard (`if (canon === "") continue;` after canonicalizing) and the key is also persisted into the dismissal setting. Add a test with `***` and `###` rows (no series, no flag).

## Should-fix (not blocking, do if touching the files anyway)

3. **Fail-soft isolation in both pages.** `app/page.tsx` and `app/forecast/page.tsx` compute `toUiDetection(...)` in the same `try` as `toUiLedger(...)`, before it. A throw there (for example an invalid `nextExpected` date reaching `toISOString()`) would blank the whole agenda, not just the add-on, contradicting the request's "fail-soft everywhere". Move the `toUiDetection` call into its own small `try` after the ledger is built (set `upcomingDetection = null` on failure). No throw is known today.
4. Rename/clarify the "Already recorded" answer for a second same-named series on another account (see defect 4 below) only if the wording is cheap to change; otherwise leave.

## Review against the requested checks

- **Ground rule 1 (no fabrication): pass.** Every amount is a median of real rows, every date derives from real posting days; a low-confidence or annual series gets no date on the calendar; Add builds the row from server-derived values only.
- **Rule 5 / security: pass.** All three exports start with `await requireAuth();` (local helper identical to `actions/recurring-expenses.ts`, source-pinned by a test). The client sends only `{ entityId, seriesKey }` (zod uuid + max length + key-prefix check); the server re-runs the loader and detector, refuses missing/suppressed/inflow series, and no client amount, name, frequency, date or tag reaches the write (tester injected-field tests). No AuditLog row (matches the neighbour action; no payee text can leak). The only `console.error` logs `err.name`. Series keys carry internal ids (uuids), not account numbers; the UI scan found no account numbers, emails or 6+ digit runs. Dismissal JSON is parsed fail-soft.
- **Rule 6 (personal/business separation): pass.** Group key is entity + account + sign; suppression and flags use same-entity refs only; the all-entities view shows no blended money in the learned heading and per-entity chips; a dismissed key is never matched across entity or account.
- **Rule 8 (observational wording, no advice): pass.** "Looks recurring", "usually", "about", footer "These are patterns, not bills"; no "should"/"CPA"/"recommend" in any new string (Tester live scan of 800+ strings plus my read of the components).
- **Learned strictly outside totals: pass.** `learned` is a separate array; step 9 of `buildUpcomingLedger` only reads `kept` and never writes to `items`/`undated`/`pastDue`/`totals`/`totalsByEntity`/`biggest`. I read the diff: the new code is additive, existing returns gain three fields, and the existing five test files pass unmodified plus the Tester's HEAD differential (400 fuzzed inputs byte-identical).
- **Fail-soft: pass except should-fix 3.** The detection reads are in a caught promise; pure detector throws are caught in the loader; the pages' own try/catch remains; the "unavailable" notice is render-tested.
- **Money as Decimal, UTC/NY dates: pass.** Decimal throughout, `getUTC*` only (source-scan test; mutant "local-time dates" killed); the loader maps `todayForNewYork(now)`; display formats via the view's existing date helpers.
- **AppSetting dismissal safety: pass.** One key per entity (`recurring_dismissed:{entityId}`), value is JSON capped at 200 (oldest dropped, tested through the real wrapper), unreadable value reads as empty, the read-modify-write race can only resurrect a suggestion (harmless), keys are internal ids + canonical payee only, restore is harmless when not dismissed. It uses `upsert` on `AppSetting`, which is the repo's existing setter. The prefix/token match for dismissed keys is scoped to the same entity, account and sign.
- **Coder's deviations: all justified.** (1) Two extra files because a guard test forbids other importers of `lib/upcoming-ledger-build` and because importing the buttons from the widget pulled next-auth into vitest; both existing test files remain unmodified. (2) Annual must be fixed-amount: sound, evidenced by a live false positive (convenience store). (3) Day-rule text fix: correct. (4) A price rise stays a fixed series: needed for the "2 in a row" flag. (5) The extra conservative flag rules (stop after 3 short cycles, 75-day stopped-bill rule, dominant-payee tag matching, 4+ matches for "history differs") only reduce false alarms. (6)-(8): fine. Deviation 7 (Add allowed for annual) is acceptable because it is an explicit owner click; note the plan's own test list required it.
- **Scope discipline: pass.** No change to `lib/forecast.ts`, `lib/business-forecast.ts`, `lib/notifications.ts`, `prisma/**`, `actions/recurring-expenses.ts` or advisor files. CLAUDE.md change is one new paragraph plus the one corrected sentence in "Upcoming ledger" (word-diff confirmed: only "defined but never produced" became "produced only by the recurring detector ... and never enters a total").
- **Documentation: pass.** CLAUDE.md covers the module split, invariants, flags and the no-migration dismissal choice.
- **Test quality: strong.** 114 Coder tests plus 100 Tester tests; oracle fuzz of 2,500 series, 80 detector mutants and 11 ledger mutants all killed, HEAD differential, source-reading pins for `requireAuth()` and purity. The one gap is exactly required 1 and 2 (no test with issuer-specific card-payment descriptors or an empty canonical name).
