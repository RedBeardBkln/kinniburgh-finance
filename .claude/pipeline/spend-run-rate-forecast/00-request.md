TASK: Build a historical-spend run-rate forecasting engine.

CONTEXT: This is Tier 1, item 1 of an agreed product roadmap toward the platform's north star: "automate as much financial work as possible" via forecast projections based on historical spending + budgets. The codebase already has a SCHEDULE-based cash-flow forecast (lib/forecast.ts — projects account balances from known recurring transfers/bills/income) and a THRESHOLD-based budget check (lib/notifications.ts checkBudgetOverspend — alerts at 80%/100% of budget used-to-date, no forward projection). What's missing, and what this task builds, is a TREND-based projection: given a tag's actual spending history, project where it will land by the end of the current period, before the period ends.

DATA AVAILABLE: Real production data already exists — 3,463 transactions spanning May 2025 to Sep 2026 (16 months), tagged and budgeted, synced daily via Plaid. Plenty of history to build against. (You don't need DB access to plan this — it's a pure function over inputs the caller will supply.)

REQUIREMENTS:
1. New lib module (e.g. lib/spend-forecast.ts) with a pure function that, given a tag's transaction history (trailing N months, N configurable, reasonable default e.g. 3) and the current period's spend-to-date, projects the likely end-of-period total. Use a sensible method (e.g. linear pace extrapolation from days-elapsed vs days-in-period, blended with a trailing-average baseline per tag to smooth single-month noise) — document the method's assumptions in a short comment, since this is financial guidance data (CLAUDE.md ground rule 8: observational, never advice, never framed as a guarantee).
2. Must follow CLAUDE.md conventions: TypeScript strict, money as Decimal (never floats — see lib/budget.ts's computeBudgetSummary for the existing pattern), pure function tested in lib/__tests__/ following existing test file patterns (see lib/__tests__/budget.test.ts and lib/__tests__/forecast.test.ts for style — no DB in unit tests, mock at the function boundary).
3. Unit tests covering: steady/level spending, front-loaded spending (e.g. rent paid day 1), back-loaded spending, a tag with no history yet (should not crash or wildly extrapolate from zero data), and a tag that's already over budget.
4. Do NOT wire this into notifications or the UI yet — scoped to the core projection module + tests only, so it can be reviewed on its own merits before deciding how it surfaces (that's a separate follow-up task).
5. Do not touch the Prisma schema. Do not add new dependencies unless something already in package.json is insufficient (check first — Decimal.js is already used via lib/budget.ts's import, reuse that same pattern).
6. Definition of done: pnpm typecheck, pnpm lint, and pnpm test (full suite) all pass clean, matching the project's existing 289/289 passing baseline (the new tests add to that count).

Read lib/budget.ts, lib/forecast.ts, lib/notifications.ts (checkBudgetOverspend specifically), and their corresponding test files in lib/__tests__/ before planning, so your plan matches the existing code's actual shape (interfaces, Decimal usage patterns, date-handling conventions) rather than guessing. Produce a concrete, scoped implementation plan: the exact function signature(s)/types to add, the projection algorithm in enough detail that the Coder doesn't have to make design decisions, and the specific test cases (with rough expected-value reasoning) to write.
