Task slug: budget-parent-auto-sum

Let a parent budget line be added without an amount, and when blank, auto-compute it as the sum of its nested child budget lines' amounts (recursively) — while making sure entity/account/monthly budgeted totals don't double-count a parent and its children.

CONTEXT (already investigated by the orchestrator this session — verify current code state but trust this diagnosis, don't re-derive it from scratch):

**Just shipped this session (reuse, don't rebuild):** `lib/budget-nesting.ts#nestBudgetLines()` — a pure function that, given an account's flat budget-line list and a `tagId -> parentId` lookup, nests a line under another line in the SAME account whose tag is its direct parent (e.g. "HBO Max" nests under "Streaming" when both are budgeted on the same account; a tag with no budget line of its own never pulls its descendants up). It returns `{ line, depth }[]` in parent-first/depth-first order. It's wired into `components/budgets/budget-page-client.tsx` (rendering) via `app/budgets/page.tsx` (which now also serializes `Tag.parentId` and queries `budgetedTagIdsAllEntities` — a cross-entity-wide "already used this period" set added in the same recent pass). This existing children-of-a-tag relationship building is exactly what the new auto-sum feature needs to reuse or extend — don't reinvent parent/child matching from scratch.

**The owner's exact request (verbatim):**
> Allow the ability to add a parent budget line to a budget without being required to include an amount. And if the amount for the parent is blank it should automatically sum up all of the budgeted amounts of the child budgets nested underneath it. For example, the amount for the parent budget line "Food & Drink" would be the sum of Groceries and Restaurant budget lines. Likewise, Restaurants would be the sum of Bakeries & Coffee Shops, Food Delivery, Gas Stations, Restaurants - Both, etc. The budgeted total for the month would also need to make sure it doesn't sum up the parents and the children together so they don't get double counted.

This is explicitly RECURSIVE/multi-level: "Food & Drink" (blank) sums its direct children ("Groceries" + "Restaurants"), where "Restaurants" (itself possibly blank) sums ITS OWN children ("Bakeries & Coffee Shops" + "Food Delivery" + "Gas Stations" + "Restaurants - Both" + ...). Resolution must happen bottom-up, arbitrary depth, matching `nestBudgetLines`'s existing multi-level support (see its test file `lib/__tests__/budget-nesting.test.ts` for the 3-level "Utilities → Internet and Phone → Cell Plan" style precedent already established).

**Schema change required:** `prisma/schema.prisma`'s `Budget.budgeted` is currently `Decimal @db.Decimal(14,2)` — NOT NULL, required. It needs to become nullable (`Decimal? @db.Decimal(14,2)`) so "blank" is a real, distinguishable state (not a sentinel `$0`, which would be ambiguous with a deliberately-zero-budgeted line). **This needs a real Prisma migration.** No existing rows need backfilling — every current `Budget.budgeted` value is already non-null, so the migration is a pure type-relaxation (no data change). Apply the same migration-push-gate caution as the `accrual-draw-dates` task earlier this session: hand-write the migration SQL, do NOT run `prisma migrate dev`/`db push` against the shared local/production Supabase instance, and do not push the commit without the orchestrator's explicit go-ahead.

## Required behavior

1. **Schema**: `Budget.budgeted` becomes nullable. Hand-written migration, not applied to the DB by the Coder (migration-push-gate).
2. **UI**: `components/budgets/budget-edit-modal.tsx`'s "Monthly Budget" field must be genuinely optional in both add and edit mode (currently the zod schemas in `actions/budgets.ts` — `CreateSchema`/`UpdateBudgetSchema`/`UpdateSchema` — require `budgeted` to match `/^\d+(\.\d{1,2})?$/`, which rejects an empty string; these need to accept blank/undefined meaning "auto"). In edit mode, a currently-blank/null `budgeted` should show as an empty field (not "0.00"), so the owner can see it's in auto-sum mode. Consider adding a short UI hint near the field (e.g. "Leave blank to auto-sum nested budget lines") — your call on exact copy/placement.
3. **Resolution algorithm**: a new pure function (likely in `lib/budget-nesting.ts` alongside `nestBudgetLines`, reusing its parent/child relationship building rather than duplicating it) that, given an account's budget lines (each with a possibly-null `budgeted`) and the tag-parent lookup, resolves every line's EFFECTIVE amount bottom-up: a line with a non-null `budgeted` uses it as-is; a line with null `budgeted` resolves to the sum of its direct children's ALREADY-RESOLVED effective amounts (recursing as needed); a null-budgeted line with no matching children in this account resolves to $0. Write this so it composes cleanly with `nestBudgetLines`'s existing tree-building (don't build two separate, potentially-inconsistent parent/child trees).
4. **No double-counting in totals**: apply the fix described in consumer #1 and #2 above — any "total budgeted" figure (whole-entity monthly total, per-account subtotal, business-forecast projected-expense total) must sum only root-level resolved amounts, never root + descendants together.
5. Ground rule 8 (observational language) is probably not directly implicated here (this is arithmetic, not a forecast/projection claim) but keep it in mind if the UI surfaces any new "projected" language.
6. Ground rule 1 (never fabricate data) — do not invent or backfill any blank amounts on the owner's behalf; ship this so *he* can leave a line blank going forward. No existing budget lines should be modified/nulled by this change.
