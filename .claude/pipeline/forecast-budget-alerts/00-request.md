Task slug: forecast-budget-alerts

TASK: Wire the historical-spend run-rate forecasting engine (lib/spend-forecast.ts, already built, reviewed, and merged in a prior pipeline task) into the notification system (lib/notifications.ts), so budget alerts become forecast-aware instead of purely threshold-based.

CONTEXT: This is Tier 2, item 1 of an agreed product roadmap toward the platform's north star: "automate as much financial work as possible" via forecast projections that keep both household members informed. lib/spend-forecast.ts exports `projectPeriodEndSpend()` — given a tag's trailing-months monthly spend history plus current period-to-date spend, it projects the likely end-of-period total, with a `confidence: "low"|"medium"|"high"` field and a `method: "blended"|"pace_only"` field. Read lib/spend-forecast.ts and lib/__tests__/spend-forecast.test.ts fully to understand its exact signature and semantics before planning — do not guess at it.

lib/notifications.ts's existing `checkBudgetOverspend(period)` function queries current-month actual spend per tag (via a raw SQL GROUP BY tagId query already in that file) and fires a notification when `percentUsed >= 80` — this is a snapshot/threshold check ("you've used 80% of budget"), not a forecast ("you're on pace to land at $X by month end"). Read lib/notifications.ts in full (especially checkBudgetOverspend and the helper functions it calls: computeBudgetSummary from lib/budget.ts, alreadyNotifiedToday, createNotification, getAllUserIds, daysRemaining) and its test file lib/__tests__/notifications.test.ts before planning, so the plan matches this codebase's actual patterns rather than inventing new ones.

DESIGN QUESTIONS FOR YOU TO RESOLVE (make a concrete decision, don't leave these open for the Coder):
1. Does forecast-awareness enrich the EXISTING checkBudgetOverspend notification (e.g., add a projected end-of-period figure to the body/payload when available), or does it become a SEPARATE new check/notification type (e.g., checkBudgetPace / "trending over budget") that can fire independently of and earlier than the 80%-used threshold? Consider: spec 05's proactive-guidance feature explicitly wants an 80%/100%-of-budget-used alert AND the product roadmap separately wants forward pace warnings — these are two distinct signals a household would want to see (e.g., "only 20% used but it's day 3 of the month and pace says you'll blow the budget" is a real, valuable, EARLIER warning that a pure threshold check cannot produce). Decide based on what serves the actual notification value, and justify your choice in the plan.
2. Where does the trailing-months monthly spend history (the `MonthlySpendPoint[]` that projectPeriodEndSpend needs) come from? It must be computed from real DB data (the Transaction/TransactionTag tables), following the same raw-SQL-GROUP-BY-tagId pattern already used in checkBudgetOverspend for current-month spend — plan the exact query needed to get trailing N months of spend per tag.
3. How does `confidence` factor into whether/how a forecast-based alert fires? (e.g., should a "low" confidence projection early in a sparse-history period be suppressed rather than alarm the household with a shaky number? Decide and justify.)
4. Ground rule 8 (CLAUDE.md): notification copy must stay observational, never advice ("Groceries is projected to reach $1,340 by month end based on current pace" — not "you should cut back on Groceries"). Specify the exact notification body template(s).
5. Respect existing anti-spam pattern: reuse `alreadyNotifiedToday(scopeKey)` with an appropriately distinct scopeKey so this doesn't double-fire alongside the existing overspend check for the same tag/period.
