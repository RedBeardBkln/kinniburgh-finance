# Request

Tier 4 "mobile PWA polish," part 2 of 3 (part 1, offline resilience, shipped in commit `7b87b67`). This part: installability / home-screen experience. Part 3 (mobile-responsive layout audit) is a separate later task.

## Current state (verified by the orchestrator — don't re-derive)

- `app/manifest.ts` provides a correct manifest: `standalone` display, theme color, `start_url: "/"`. Icons: `web-app-manifest-192x192.png` and `web-app-manifest-512x512.png`, each declared TWICE — once with `purpose: "any"` and once with `purpose: "maskable"`, both entries pointing at the exact same image file.
- `app/layout.tsx` sets `appleWebApp: { capable: true, statusBarStyle: "black-translucent", title: "Banana Stand" }` and an `apple` icon pointing at `/apple-touch-icon.png` (or `/api/logo` if a custom logo is set — see below).
- **Icon file dimensions are all already correct** — verified directly by reading PNG headers: `apple-touch-icon.png` is 180×180 (Apple's recommended size), `web-app-manifest-192x192.png` is 192×192, `web-app-manifest-512x512.png` is 512×512, `favicon-96x96.png` is 96×96. No dimension bugs.
- **Confirmed real bug: the maskable icon has no safe-zone padding.** Android's adaptive-icon system crops a `purpose: "maskable"` icon to a circle/squircle mask, showing only the center ~80% "safe zone" — anything near the edges gets clipped. The orchestrator viewed `web-app-manifest-512x512.png` directly: it's the full "Banana Stand" logo (a banana-costume mascot + banner text reading "BANANA" at the top and "STAND" at the bottom) rendered full-bleed edge-to-edge, with the text banners coming close to the image border. Reusing this exact file for the `maskable` purpose entry means Android home-screen icons will very likely clip the "BANANA"/"STAND" text. This needs a dedicated, separately-generated maskable variant with the logo content scaled down and centered inside a safe zone, on a canvas filled edge-to-edge with a solid/background color (not transparent, not the full-bleed art) so it doesn't look broken when cropped.
- **No custom install-prompt UI exists at all.** Confirmed via repo-wide grep: zero references to `beforeinstallprompt` or `appinstalled` anywhere in `app/`/`components/`. Installability today relies entirely on each browser's native default UI (Chrome's address-bar install icon, Android's automatic "Add to Home Screen" banner, Safari's manual "Add to Home Screen" share-sheet action — which Safari doesn't support `beforeinstallprompt` for at all, so no custom UI is possible/needed there; that event is Chromium-only).
- `sharp` (^0.35.4) is already a real dependency (used elsewhere for image processing — see `lib/supabase-storage.ts`/logo-upload code) and available for generating the new maskable icon variant programmatically.
- The app has an EXISTING, SEPARATE custom-logo-upload feature (`app/settings/branding/page.tsx`, `/api/logo`, `lib/settings.ts`'s `getLogoMeta`) that lets a user replace the browser-tab favicon/apple-touch-icon with their own uploaded image. **This is intentionally NOT wired to the PWA manifest icons** (`app/manifest.ts` hardcodes the static `web-app-manifest-*.png` files, not `/api/logo`) — leave this separation exactly as-is; this task is not about branding customization, don't connect these two systems.

## Scope

**In scope:**
1. Generate a proper maskable-safe-zone variant of the icon (both 192×192 and 512×512) using `sharp` — content scaled/centered within roughly the inner 80% of the canvas, background color filling the full canvas edge-to-edge (use the manifest's existing `background_color`/`theme_color` value, `#d97706`, unless the source art has its own dominant background color that would look more correct — use judgment, but must not be transparent). Update `app/manifest.ts` so the `maskable` purpose entries point at the new files, while `any` purpose entries keep pointing at the original full-bleed files (both are still needed — `any` is used by non-masking contexts like browser install icons/taskbars where the full art should show).
2. A custom, Chromium-only "Install app" prompt: capture the `beforeinstallprompt` event (call `.preventDefault()` on it and stash the event), show a small dismissible UI affordance (banner or button) offering to install, and call `.prompt()` on user action. Must gracefully do nothing on browsers that never fire the event (Safari, Firefox) — no broken/dead UI shown there. Also listen for `appinstalled` to hide the prompt UI once installed. Follow this repo's existing pattern for small always-mounted client components (see `components/global-error-safety-net.tsx`, `components/offline-indicator.tsx` from the just-shipped offline-resilience task) for style/structure precedent.

**Explicitly out of scope:**
- No iOS/Safari custom install UI — `beforeinstallprompt` doesn't exist there; do not attempt to build a custom "Add to Home Screen" instruction overlay for Safari (a bigger, more opinionated UX decision the user hasn't asked for — flag as a possible future idea in the plan's notes if you think it's worth it, but do not build it).
- No `apple-touch-startup-image` splash-screen generation — high-maintenance (many exact device-pixel sizes), low value for a 2-person household app, not requested.
- No changes to the branding/custom-logo feature.
- No changes to `public/apple-touch-icon.png` or `public/favicon*` — those are correctly sized already and this task is scoped to the manifest's maskable-icon entries specifically.
